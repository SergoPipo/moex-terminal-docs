Дата: 2026-10-23. Статус: **передан в проект Moex 2026-10-23**; дополнение по дилерским часам — после 25.10.2026.

Документ собирает решения, принятые по итогам разбора торгового терминала, данных MOEX ISS и T-Invest API и кода
Moex-Terminal (2026-10-17 … 22). Для каждого пункта: что делаем и почему (замеры), где в коде Moex, как проверяем, от
чего зависит, на каком этапе.

**Как пользоваться.**
- Раздел 1 — сводная таблица всех пунктов; раздел 2 — порядок работ по этапам и сквозные правила (2.1); раздел 3 —
  пункты подробно по блокам;
  раздел 4 — найденные дефекты; раздел 5 — отложенное и то, что не делаем; раздел 6 — приложения.
- Номера пунктов (A1, B3, …) сквозные: по ним пункты ссылаются друг на друга.
- Это рекомендуемая очерёдность и описание решений, а не план с датами: сроки и разбивка на задачи — при планировании в
  проекте Moex.
- Код Moex при разборе только читался, все замеры — только чтение данных и API (без заявок).
- Файлы пакета лежат в одной папке: этот документ; `addendum_dealer_hours.md` — дополнение по дилерским часам
  («Перед началом реализации», п. 3); `d8_news_labels.json` — данные из приложения 6.1.

## Перед началом реализации

**1. Сверка с текущим кодом Moex — обязательна для каждого пункта.** Документ составлен по коду и данным Moex на
22–23.10.2026: файлы, функции, номера строк, таблицы и числа в разделах «Факты» и «Где в коде Moex» относятся к этому
состоянию. Перед реализацией пункта:
- найти в текущем коде все места, названные в пункте, и убедиться, что они устроены так, как описано;
- если код с тех пор изменился (файл переименован, логика уже переделана, часть пункта уже сделана) — записать
  расхождение и **согласовать с владельцем проекта**, прежде чем менять решение; решения пакета молча не пересматривать;
- номера строк — ориентир, а не адрес: искать по имени функции или класса.

**2. Начинать можно до итога проверки дилерских часов.** Проверка в выходные 24–25.10.2026 (принимает ли API заявки в
часы дилера, спред дилера, помечает ли поток T-Invest источник свечи — биржа или дилер) касается только трёх мест:

## 1. Кратко

**Что меняем.**
- **Данные:** основной ряд — только биржевые свечи, объём в штуках, хранение 1m + D и сборка остальных ТФ, торговые
  часы с утренней сессией и выходными, дивиденды с ручными поправками.
- **Безопасность live:** стопы внутри бара, «Стоп всему», уровневые алерты по пересечению.
- **Исполнение и движок:** один договор исполнения для бэктеста, paper и будущего движка; дивиденды в бэктесте; свой
  единый движок стратегий вместо backtrader (лицензия GPLv3+).
- **Индикаторы и стратегии:** 87 индикаторов на графике одной библиотекой со стратегиями, свои индикаторы (с генерацией
  ИИ), входы с границами, проверка «без заглядывания вперёд», отчёт «что не перенеслось».
- **События, сигналы, гейты:** календарь событий, фильтр событий в стратегиях, импорт сигналов, сигнальный режим, гейт
  качества перед real, размер позиции «риск на сделку».
- **Алерты и новости:** алерты по условиям индикаторов и от трендовых линий, закрытый бар по умолчанию, лента новостей
  по всему рынку с ИИ-разметкой.
- **Скринер:** по всему рынку с фильтром ликвидности, тепловая карта, сектора, фундаментал, карточка компании.
- **Графики:** несколько графиков на экране, виды и шкалы, сравнение бумаг, рисунки на всех ТФ, новые инструменты,
  реплей, пошаговый разбор бэктеста и ИИ-разбор сделок.

## 2. Порядок работ

```

Действуют для всех пунктов раздела 3 (приняты 2026-10-23 по итогам проверки на однозначность). Уточнения

### 3.1. Данные и бары

#### Хранение баров: решения 1–5

*Этап:* 1 (решение 4 = A1, решение 5 = A2). Решения приняты 2026-10-19.

##### Решение 1. Таблица покрытия вместо эвристики `_find_gaps`

**Проблема.** `MarketDataService._find_gaps` определяет недогруженные места по разрывам между барами
с допуском: 14 ч для 1m/5m/15m, 65 ч для 1h, 16 ч для 4h, 5 дней для D. Поэтому:
- дыры внутри дня меньше допуска не дозапрашиваются никогда (SBER: 39 пропущенных 5m-баров в основной
  сессии будней; 1h, собранный из такого 5m, не совпадает с T-Invest на 2–3%);
- эвристика не отличает «не загружено» от «сделок не было» (в минутках неликвида это обычное дело);
- хвост обновляется по отдельным допускам `tail_tolerance`.

**Решение.** Явно хранить, какие диапазоны загружены из источника полностью.

```
ohlcv_coverage
  id           INTEGER PK
  ticker       VARCHAR(20)   -- канонический тикер, как в ohlcv_cache
  timeframe    VARCHAR(10)
  source       VARCHAR(20)   -- tinvest | tinvest_dealer | moex_iss (дилерский ряд — 2026-10-23)
  range_from   DATETIME      -- UTC, включительно
  range_to     DATETIME      -- UTC, не включительно
  loaded_at    DATETIME
  INDEX (ticker, timeframe, source, range_from)
```

Правила:
1. После успешной загрузки `[from, to)` записывается покрытие `[from, min(to, начало текущего
   формирующегося бара))`. Формирующийся бар покрытым не считается никогда.
2. Пересекающиеся и смежные диапазоны одного (ticker, timeframe, source) сливаются в один.
3. `get_candles`: загружать нужно только «запрошенный диапазон минус покрытие». Отсутствие баров внутри
   покрытого диапазона означает «сделок не было», повторный запрос не делается.
4. Хвост от последнего закрытого бара до текущего момента всегда считается непокрытым (заменяет `tail_tolerance`).
5. Частичная загрузка (`TransientBrokerError`, `RateLimitExhaustedError` с `partial_candles`) записывает
   покрытие только для фактически полученных непрерывных кусков.
6. Любое удаление свечей удаляет соответствующее покрытие в той же транзакции: `_purge_iss_cache`,
   будущие data-миграции по образцу `6f3a063d1c2e` и `e1f2a3b4c5d6`.
7. Миграция: для существующих строк покрытия нет, они считаются непокрытыми и дозагружаются по запросу
   (upsert T-Invest-строк это допускает).

Где менять: `app/market_data/models.py` (новая модель), новая alembic-миграция,
`app/market_data/service.py` (`_find_gaps` → вычитание покрытия, `_save_to_cache` пишет покрытие,
`_purge_iss_cache` чистит его).

Тесты: дыра внутри дня дозапрашивается; пустые минуты внутри покрытого диапазона не дозапрашиваются;
формирующийся бар не попадает в покрытие; очистка кэша удаляет покрытие; частичная загрузка покрывает
только полученное.

##### Решение 2. Удалить дублирующий индекс `idx_ohlcv_lookup`

**Проблема.** На `ohlcv_cache` два одинаковых индекса по (ticker, timeframe, timestamp):
`sqlite_autoindex_ohlcv_cache_1` от `UniqueConstraint(..., name="uq_ohlcv_lookup")` и обычный
`Index("idx_ohlcv_lookup", ...)`. Каждый по 19,1 МБ: 181 байт на строку вместо ~134 (+35% к объёму),
каждая вставка обновляет оба индекса.

**Решение.** Оставить только индекс уникальности. Сейчас SQLite выбирает `idx_ohlcv_lookup`
(`EXPLAIN QUERY PLAN`: `SEARCH ohlcv_cache USING INDEX idx_ohlcv_lookup (ticker=? AND timeframe=?
AND timestamp>? AND timestamp<?)`). После удаления он возьмёт автоиндекс уникальности с теми же колонками
в том же порядке, план запроса не изменится.

Где менять:
- `app/market_data/models.py`: убрать `Index("idx_ohlcv_lookup", ...)` из `__table_args__` `OHLCVCache`
  (иначе alembic autogenerate создаст его снова);
- новая alembic-миграция: `batch_alter_table("ohlcv_cache")` → `drop_index("idx_ohlcv_lookup")`,
  downgrade создаёт его обратно;
- `app/trading/unrealized.py:141`: комментарий ссылается на `idx_ohlcv_lookup`, заменить на индекс уникальности.

Проверка после миграции: `EXPLAIN QUERY PLAN` запросов свечей использует индекс уникальности;
размер индексов `dbstat` уменьшился на ~19 МБ. Чтобы уменьшился сам файл БД, нужен `VACUUM`
(SQLite не возвращает освободившиеся страницы сам) — выполнять в окне обслуживания.

##### Решение 3. Хранить 1m и D, остальные таймфреймы собирать из них

**Проблема.** Каждый таймфрейм сейчас запрашивается у T-Invest и хранится отдельно (6 кэшей со своими
дырами), а live-стрим строит 1h/4h/D из 1m. Бэктест и live видят свечи из разных источников; набор
таймфреймов ограничен тем, что хранится; нестандартные таймфреймы невозможны.

**Решение.**

```
ХРАНИТЬ в ohlcv_cache (родные свечи T-Invest)    СОБИРАТЬ при чтении
1m ──────────────────────────────────────────►  5m 15m 30m 1h 4h (набор утверждён в G3, 2026-10-20)
D  ──────────────────────────────────────────►  W, M
```

Уточнение 2026-10-20 (G3 и G4): нестандартные ТФ не делаем; набор ТФ — 1m, 5m, 15m, 30m, 1h, 4h, D, W, M
(к нынешним восьми добавляется только 30m; 2m, 3m, 10m, 2h и поле своего ТФ не делаем).

Правила агрегации (проверены на кэше, раздел 2):
1. O = первый бар, H = max, L = min, C = последний, V = сумма. Группа без 1m-баров даёт отсутствие бара,
   как у T-Invest.
2. Внутридневные корзины выравниваются по кратным интервала от начала эпохи в UTC: 1h — по часу UTC,
   4h — 00/04/08/12/16/20 UTC (03/07/11/15/19/23 МСК, совпадает с T-Invest).
3. W — неделя с понедельника, M — календарный месяц, обе собираются из D.
4. Последняя корзина, в которую ещё приходят 1m, помечается формирующейся и не кэшируется как закрытая.

Один агрегатор на всё:
- вынести `_candle_period_start` и `_AggregatingCandle` из `app/market_data/stream_manager.py` в общий модуль
  (например, `app/market_data/aggregation.py`) с пакетной функцией `aggregate(bars_1m, timeframe)`;
- его используют и `MarketDataService.get_candles` (история), и стрим (live).

Где менять:
- `app/market_data/service.py`, `get_candles`: для производного ТФ загрузить 1m (или D для W/M) через кэш
  с покрытием (решение 1) и вернуть агрегат. Все потребители (`market_data/router.py`, `prefetch.py`,
  `backtest/engine.py`, `backtest/router.py`, `backtest/benchmark.py`, `trading/runtime.py`) ходят через
  этот метод, их менять не нужно;
- `TIMEFRAME_DURATIONS`: добавить 30m (G3, 2026-10-20);
- фронтенд: тип `Timeframe` в `src/api/types.ts`, `TimeframeSelector.tsx`, список внутридневных ТФ
  в `components/charts/sequentialIndex.ts`;
- результат агрегации держать в памяти (LRU по ticker + tf + диапазон), в БД не писать.

Миграция данных:
- строки 5m, 15m, 1h, 4h в `ohlcv_cache` становятся ненужными: удалить data-миграцией по прецеденту
  `6f3a063d1c2e` / `e1f2a3b4c5d6` после включения агрегации (это производный кэш);
- 1m догружать фоном: будни массово через архивы T-Invest (`history-data?figi=`, 30 запросов/мин),
  выходные и праздники — через `GetCandles` с `CANDLE_SOURCE_INCLUDE_WEEKEND` и раскладкой по источнику, как в решении 4
  (в архиве они смешаны с дилерскими, раздел 6.3; исправлено 2026-10-23); точечные дозагрузки — `GetCandles` окнами по 1 дню с учётом лимита MarketDataService
  (600/мин) и существующего `rate_limit_wait`;

  исключений «хранить родной ТФ для глубокой истории» не нужно (раздел 6.2).

##### Решение 4. Основной ряд — только биржевые свечи, дилерские — отдельно, объём в штуках

Принято 2026-10-19 (пункт A1 пакета разбор 00, вариант «биржа + дилер отдельно»). Факты — раздел 6.1 и
A1.

**Проблема.** Moex не передаёт `candle_source_type` ни в `GetCandles` (`broker/tinvest/adapter.py`), ни в
подписке (`broker/tinvest/multiplexer.py`, `SubscribeCandlesRequest`) и не хранит источник свечи. Поэтому в
выходные внутридневные бары — смесь биржевых (10:00–19:00 МСК) и дилерских свечей Т-Банка (02:00–10:00 и
19:00–23:50 МСК). Дилерская цена — цена внутреннего рынка брокера, на Мосбиржу эти сделки не попадают:
отклонение от средней биржевой цены дня — медиана 0,06–0,67%, максимум 2,68% (GAZP, 17–18.10.2026). В кэше Moex
таких баров не меньше 68 тыс. (5m 40 353, 15m 22 980, 1h 4 581 — суббота и воскресенье вне 07:00–16:00 UTC).
Объём T-Invest — в лотах (`broker/tinvest/mapper.py:290`), ISS — в штуках (GAZP: в 10 раз меньше).

**Решение.**

```
T-Invest GetCandles / подписка с CANDLE_SOURCE_INCLUDE_WEEKEND (один запрос)
        │  у каждой свечи — поле источника
        ├── EXCHANGE ────────► ohlcv_cache — основной ряд

Правила:

2. В `ohlcv_cache` пишутся только свечи с источником `EXCHANGE`. Неизвестное значение источника в основной ряд

3. Дилерские свечи — **отдельная таблица** `ohlcv_dealer` (те же колонки, только 1m; другие ТФ для графика

### 3.2. Безопасность live

#### C1. Стопы и тейки в sandbox и real

*Этап:* 1 (шаг 2 «стопы у брокера» — этап 4) · *Статус:* ✅ делаем (принято 2026-10-20)

**Факты.** Уровни SL/TP в Moex — фиксированные цены от цены входа (`calc_sl_tp_prices`: вход ± процент), трейлинга
нет. `_SessionListener._run` (`app/trading/runtime.py`) складывает обновления формирующегося бара в буфер, а
`RiskMonitor.check_sl_tp` вызывается только на закрытом баре. Касание — по high/low (`low ≤ стоп`, равенство тоже
считается), выход — market в момент закрытия бара. Оценка по кэшу (SBER, GAZP, LKOH, с 2025 года): в среднем выход
на close даже на 0,05–0,32% лучше уровня, но в 10% случаев хуже уровня на 0,27–1,50%, максимум до 6,4% на D; у тейка
в 10% случаев недобор 0,5–3,1%. Бэктест и paper выходят ровно по уровню, поэтому live расходится с ними на хвостах.

**Решение, шаг 1 (вариант 1): проверка SL/TP на каждом обновлении цены.**
- Уровни сравниваются с ценой **на каждом обновлении** формирующейся свечи из потока: для лонга `low ≤ стоп` и
  `high ≥ тейк`, для шорта зеркально. Касание → сразу встречный market-ордер через `OrderManager.close_position`,
  конца бара не ждём.
- **Сигналы стратегии** (вход и выход по условиям индикаторов, `ir.exit`) считаются как раньше — **только на закрытом
  баре**. Внутри бара индикаторы не пересчитываются: на недостроенном баре сигнал «мигает», бэктест считает по
  закрытым барам, обновлений десятки в секунду.
- Проверка на закрытом баре остаётся страховкой: если обновление было пропущено и уровень пробит, позиция
  закрывается на закрытии бара, как сейчас.
- Часы — по A5: внутри бара закрытие разрешено во все часы, когда разрешены выходы, включая аукцион.

**Решение, шаг 2 (вариант 2): флажок «Стоп и тейк держать у брокера».**
- **Где:** настройка торговой сессии — в форме запуска и в карточке сессии. Только sandbox и real (в paper брокера
  нет). По умолчанию выключен. Почему у сессии, а не общая: сначала включить в песочнице, потом в real; у бумаг
  разные условия торгов.
- **Смена на работающей сессии** действует со следующего входа. Каждая сделка помнит, кто закрывает её выход:
  «терминал» или «брокер». Открытая позиция доживает по тем правилам, с которыми открылась.
- **Что ставится:** после исполнения входа — две условные заявки T-Invest на исполненное число лотов:
  `STOP_LOSS` (уровень стопа) и `TAKE_PROFIT` (уровень тейка). При срабатывании обе отправляют рыночную заявку,
  действуют до отмены, цена округляется к шагу цены бумаги.
  - Тейк — не лимитная заявка в стакане: она блокирует бумаги (поле `blocked` в позициях), и стоп при срабатывании
    получил бы отказ «недостаточно бумаг».
  - Связки «сработала одна — отменилась другая» в API нет (в `PostStopOrderRequest` такого поля нет), поэтому
    вторую заявку снимает терминал.
- **У выхода один хозяин.** Терминал продолжает проверять касание внутри бара (шаг 1), но при флажке сам не
  закрывает, а действует так:

| Событие | Что делает терминал |
|---|---|
| Касание уровня | раз в секунду спрашивает статус условной заявки (`GetStopOrders`) |
| Заявка исполнена | по `exchange_order_id` читает исполнение (`GetOrderState`): фактическая цена и комиссия; записывает выход; снимает вторую заявку |
| Исполнена частично (рыночная заявка продала часть лотов) | записывает исполненную часть; остаток продаёт **сразу сам**, без таймера (условная заявка одноразовая, остаток без защиты, а переставить стоп за пробитый уровень нельзя); снимает висящий остаток и вторую заявку |
| Заявка всё ещё активна, когда истёк таймер страховки | снимает её и ждёт подтверждения, снимает вторую, закрывает позицию сам и присылает уведомление «стоп брокера не сработал». Закрывает, **даже если цена вернулась** — касание было, бэктест бы вышел |
| Заявка отменена или истекла | не ждёт, сразу закрывает сам |
| При снятии брокер ответил «уже исполнена» | **не продаёт**, записывает исполнение брокера |
| Нет связи с API | вслепую не продаёт, повторяет запросы, присылает уведомление |
| Выход по сигналу стратегии, вручную, аварийный стоп, остановка сессии | сначала снимает обе заявки и ждёт подтверждения, потом закрывает; если заявка уже исполнилась — второй продажи нет |
| Вход исполнился частично или размер позиции изменился | ставит или переставляет заявки на фактическое число лотов |
| Брокер не принял заявку (например, цена уже за уровнем) | выход сделки переходит к терминалу (шаг 1), уведомление |
| Перезапуск терминала | сверка с брокером: заявка без позиции — снять; у позиции нет заявки, а у брокера она исполнена — записать выход; заявки нет и не было — поставить заново |
| После любой своей продажи | сверка позиции с брокером; если появился шорт — уведомление и закрытие |

- **Таймер страховки** нужен только для случая «заявка ещё активна». Длина — из замера: время «касание → статус
  „исполнена“» × 2–3, ориентир 3–5 секунд. Это константа, а не настройка пользователя. Короткий таймер не создаёт
  двойной продажи (правило «сначала снять, потом продавать»), длинный — запаздывает с выходом, если брокер не сработал.
- **Подсказка у флажка:** защита работает и при выключенном терминале, но срабатывает по правилам брокера — в том числе
  в часы, когда сам терминал не торгует (расходится с A5, где стоп у дилера — только после проверки).

**Где в коде Moex.**
- Шаг 1: `app/trading/runtime.py` (`_SessionListener._run`) — на обновлении того же бара вызывать проверку уровней
  без запуска стратегии; `app/trading/risk_monitor.py` (`check_sl_tp`) — принимать незакрытую свечу и не
  отправлять второй закрывающий ордер, пока первый в полёте (`_EXIT_IN_FLIGHT`, `keyed_lock` уже есть); порядок с
  обработкой сигнала на закрытом баре — через `close_failed`, как сейчас.
- Шаг 2: `app/broker/base.py` и `app/broker/tinvest/adapter.py` — постановка, чтение и снятие условных заявок (боевые
  `post/get/cancel_stop_order` и песочница `post/get/cancel_sandbox_stop_order`); `app/trading/models.py` — у сессии
  флажок, у `LiveTrade` хозяин выхода и номера двух условных заявок; alembic-миграция; `app/trading/schemas.py`
  (`SessionStartRequest` и изменение настроек сессии); `runtime.py` — сверка при старте рядом с
  `_recover_orphan_exit_orders` и `reconcile_with_broker`; фронтенд — флажок с подсказкой и пометка «выход: брокер /
  терминал» в карточке позиции.

**Как проверяем.**
- Шаг 1: сессия 1h, лонг от 100, стоп 98; обновление бара с low 97,9 в 10:05 → закрывающий ордер в 10:05, а не в
  11:00; следующие обновления того же бара второго ордера не создают; сигнал стратегии считается только на закрытом
  баре; в аукцион закрытие проходит. Через месяц live — повторить оценку по журналу сделок: хвост «выход хуже уровня»
  должен сжаться до проскальзывания market, а не 0,3–1,5%.
- Шаг 2: каждый исход из таблицы — тестом с подставным брокером. В песочнице — постановка, срабатывание, статусы,
  ответ на снятие сработавшей заявки. Задержку срабатывания и частичные исполнения песочница не покажет (исполняет по
  своей модели) — их замер на минимальной реальной заявке, только с разрешения пользователя.
- Перед включением в real проверить: срабатывают ли условные заявки в утреннюю сессию, в выходные и в часы дилера;
  блокирует ли бумаги сама условная заявка до срабатывания.

**Уточнения 2026-10-23 (проверка однозначности).**
- **Стопы в часы дилера** — по итогу проверки 24–25.10 (отдельное дополнение к пакету); до него шаги 1 и 2 делаются

#### C2. Общий аварийный стоп

*Этап:* 1 · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.** По одной сессии есть «Пауза» (снимает слушателя; при позиции — диалог «закрыть и пауза»),
«Стоп» (закрыть позиции → `stopped`) и «Закрыть всё». Telegram `/closeall` закрывает позиции всех сессий, но сессии
остаются активными — следующий сигнал откроет позицию снова. Circuit Breaker по лимитам ставит на паузу свою сессию,
класс денег или все сессии (`_trigger`, `CB_SCOPE_ALL`) и закрывает позиции (`_force_close_open_positions`), но вручную
не включается, а после паузы ничто не мешает запустить новую сессию или «Возобновить»: `create_session` и
`resume_session` состояние CB не проверяют. Позиция, которую не удалось закрыть вне часов, остаётся открытой, а у
сессии на паузе слушатель снят — стоп по ней не проверяется. Единого «остановить всё» нет.

**Решение.**
- **Включение:** красная кнопка «Стоп всему» в шапке веб-интерфейса и команда `/stopall` в Telegram, обе с
  подтверждением (как у `/closeall`).
- **Порядок при включении:**
  1. Флаг «торговля остановлена» у пользователя — в БД, переживает перезапуск. С этого момента любой ордер на вход
     отклоняется, запуск сессии и «Возобновить» запрещены. Флаг ставится первым, чтобы стратегия не успела открыть
     позицию между шагами.
  2. Все активные сессии пользователя — paper, sandbox, real — на паузу.
  3. Снять недоисполненные заявки входа.
  4. Закрыть позиции сессий рыночными заявками. При флажке C1 «стоп у брокера» условные заявки снимаются прямо
     перед своей продажей.
  5. Отчёт: «закрыто N из M», что не закрылось и почему.
- **Закрываются только позиции, открытые сессиями терминала.** Бумаги, купленные на счёт вручную, не трогаются.
- **Что нельзя закрыть сразу** (вне часов торгов, отказ брокера) — в список «закрыть при открытии»: терминал
  закрывает такие позиции в первую минуту, когда по A5 разрешены выходы, и присылает уведомление. Условные заявки
  брокера (C1, шаг 2) у них до этого момента не снимаются — позиция остаётся под защитой.
- **Снятие — только в веб-интерфейсе**, кнопка «Снять стоп» с подтверждением. В Telegram снять нельзя: внешние каналы
  управления только уменьшают риск (принцип из PTQ, разбор 12). После снятия сессии **остаются на паузе**, каждая
  возобновляется вручную.
- Пока стоп включён, на всех экранах видна плашка: когда и откуда включён, сколько закрыто, что ждёт открытия торгов,
  кнопка «Снять стоп».
- `/closeall` остаётся как есть; в подсказку добавляется: «сессии продолжают работать; остановить всё — `/stopall`».

**Где в коде Moex.**
- Флаг: `app/auth/models.py` (`User`) — время включения и источник (интерфейс / Telegram) либо отдельная таблица

#### D1. Алерт на уровень цены: пересечение и проверка при создании

*Этап:* 1 (сразу общая модель алертов) · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.** `alert_crossed` (`app/market_data/price_alert_monitor.py:61`): «above» — `close >= уровень`,
«below» — `close <= уровень`, то есть «не ниже / не выше», а не пересечение; смотрится только close каждого обновления
1m-свечи стрима. При создании положение уровня относительно цены не проверяется (`PriceAlertCreate`). Окно
`PriceAlertModal.tsx` по умолчанию ставит «Выше» и текущую цену — такой алерт срабатывает на первом обновлении. Поле
цены — 2 знака (`decimalScale={2}`), а по ISS у 108 из 510 бумаг режима TQBR шаг цены меньше копейки (FEES 0,06054 при
шаге 0,00002; HYDR 0,467; IRAO 2,6595). В справочнике `instruments` Moex `min_price_increment` пуст у всех 64 бумаг.
В `price_alerts` 0 строк — переносить старые алерты не нужно. В ФТ Moex: «при пересечении».

**Решение.**
- **Пользователь задаёт только уровень.** При создании сервер берёт текущую биржевую цену, запоминает её в алерте и
  сам определяет направление: уровень выше цены — ждём роста до уровня, ниже — падения. Уровень, равный текущей цене,
  создать нельзя (подсказка «сдвиньте уровень»). Окно показывает текущую цену и что произойдёт: «↑ сработает, когда
  цена поднимется до 300 (+2,2 %)». Выбор «Выше/Ниже» из окна убирается. Сторона «до» зафиксирована при создании,
  поэтому первое касание — честное пересечение; предыдущую цену не нужно держать в памяти, логика переживает перезапуск.
- **Проверка по high/low** обновления 1m-свечи (рост — `high ≥ уровень`, падение — `low ≤ уровень`), чтобы не пропустить
  короткий укол между обновлениями. Свеча, в которой алерт создан, проверяется **только по текущей цене**: high/low
  этой минуты могли набраться до создания.
- **Только биржевые цены** (A1): дилерские свечи в выходные алерт не запускают; торги биржи в выходные (бумаги с
  `weekend_flag`) — запускают.
- **Гэп через уровень** — алерт срабатывает на первой цене за уровнем, уведомление с пометкой: «уровень 300 пройден
  гэпом, цена 305».
- **Цена в окне — с шагом цены бумаги**, а не 2 знака. Шаг заполняется в справочнике инструментов из T-Invest.
- Повтор срабатывания, свой текст, история срабатываний — не здесь, а в блоке 7 (D2–D5).

**Где в коде Moex.**
- `app/market_data/models.py` (`PriceAlert`) — цена при создании; поле `condition` остаётся, заполняет сервер;
  alembic-миграция.
- `app/market_data/schemas.py` (`PriceAlertCreate` — без `condition`) и `price_alert_router.py` (создание: текущая
  биржевая цена, направление, отказ при равенстве).
- `app/market_data/price_alert_monitor.py` — `alert_crossed` по high/low; свеча создания — по close; только биржевой
  источник (после A1).
- Справочник: заполнение `instruments.min_price_increment` из T-Invest (`GetInstrumentBy`).
- Фронтенд: `PriceAlertModal.tsx` (без выбора условия, текущая цена и подсказка направления, шаг цены бумаги),
  стрелка на линии графика (`CandlestickChart.tsx`) — по направлению с сервера.

**Как проверяем.**
- Окно открыто и сразу «Создать» — отказ «уровень равен цене».
- Цена 293,45, уровень 300 → направление «рост»; обновление с high 300,2 и close 299,9 → срабатывает.
- Цена 310, уровень 300 → направление «падение»; рост до 315 не запускает, падение до 300 — запускает.
- Алерт создан в 10:05:30, high минуты 10:05 (набран до создания) выше уровня, текущая цена ниже → не срабатывает.
- Пятница 295, понедельник открытие 305, уровень 300 → срабатывает на 305 с пометкой «гэпом».
- Дилерская свеча в выходные за уровнем — не срабатывает.
- FEES: уровень 0,0605 вводится и сохраняется без округления.

**Уточнения 2026-10-23 (проверка однозначности).**

##### 3.1. API стратегии (набросок)

```python
class Strategy(StrategyBase):
    params = {"fast": 9, "slow": 21, "stop_pct": 2.0, "trail_pct": 3.0, "max_bars": 20}

    def on_bar(self, ctx):
        fast = ctx.ta.ema(ctx.close, self.p.fast)
        slow = ctx.ta.ema(ctx.close, self.p.slow)
        macd = ctx.ta.macd(ctx.close)                      # .macd / .signal / .hist
        trend = ctx.close[0] > ctx.ta.ema(ctx.close, 200)[0]
        d = ctx.security("D")                              # старший ТФ без заглядывания
        daily_ok = d.ta.rsi(d.close, 14)[0] < 70

        if ctx.ta.crossover(fast, slow) and macd.hist[0] > 0 and trend and daily_ok:
            ctx.entry("L", "long", size_pct=50,
                      stop_pct=self.p.stop_pct, trail_pct=self.p.trail_pct)
        if ctx.ta.crossunder(fast, slow):
            ctx.close_position("L", reason="signal")
        if ctx.position.bars_held >= self.p.max_bars:
            ctx.close_position("L", reason="time")
```

| Pine | StrategyAPI |
|---|---|
| `ta.ema(close, 9)` | `ctx.ta.ema(ctx.close, 9)` |
| `close[1]` | `ctx.close[1]` |
| `ta.crossover(a, b)` | `ctx.ta.crossover(a, b)` |
| `strategy.entry("L", strategy.long)` | `ctx.entry("L", "long")` |
| `strategy.exit(..., trail_offset=...)` | `ctx.entry(..., trail_pct=...)` или `ctx.exit(...)` |
| `request.security(sym, "D", ...)` | `ctx.security("D")` |
| `var` (состояние между барами) | атрибуты `self.*` |

##### 3.2. Скорость

- Бэктест: `ctx.ta.*` мемоизируются по аргументам и считаются **один раз на весь ряд** (numpy);
  `on_bar` только читает значение на текущем индексе. Ориентир (проверить в прототипе): десятки тысяч баров/с
  для типичной стратегии в одном процессе; grid search параллелится по процессам, как сейчас.
- Live: на закрытом баре ряд дополняется, индикаторы пересчитываются на окне (замер текущего `evaluate`:
  0,1 мс на 200 свечей) или инкрементально. Задержку определяет не расчёт, а момент закрытия бара и сеть брокера.
- Стопы, тейки и трейлинг в live проверяет риск-монитор на каждом обновлении цены (внутри бара),
  в бэктесте — SimBroker по OHLC-пути или по 1m-барам (magnifier).

##### 3.3. Безопасность кода в live

- Тот же AST allow-list, что сейчас для бэктеста (`app/sandbox`), но доступен только объект `ctx`
  и `math`: без импорта, файлов, сети, времени и случайности без зерна.
- Стратегия каждой live-сессии исполняется в отдельном рабочем процессе (как бэктест сейчас) с лимитами
  памяти и таймаутом на `on_bar` (например, 50 мс); при превышении — HOLD и остановка сессии.
- Code-only стратегия допускается в live только после бэктеста и квант-проверок (гейт статуса `tested`).

##### 3.5. Pine-совместимость: готовые решения

- **PyneCore** — Python-рантайм с семантикой Pine (бар за баром, бэктест стратегий), Apache 2.0.
  Компилятор Pine → Python (PyneComp) — отдельный платный сервис. Live-торговля в описании не заявлена.
  Вариант: взять как движок или как эталон семантики; решать после короткого технического спайка.
- **PineTS** (LuxAlgo) — TypeScript, AGPL-3.0 или коммерческая лицензия; для закрытого продукта без лицензии не подходит.
- Трансляция Pine → StrategyAPI силами ИИ-ассистента — уже есть ИИ-чат; результат проходит
  бэктест и квант-проверки как любая code-стратегия.

#### B3. Одна модель исполнения для бэктеста и paper

*Этап:* 2 · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.**
- Сейчас бэктест (backtrader, `ir_codegen.py`): вход market по open следующего бара + проскальзывание; SL — `Stop`,
  TP — `Limit`, связаны отменой в `notify_order`. Paper: вход по close сигнального бара без проскальзывания
  (`_fill_paper_trade_locked`), SL/TP ровно по уровню на закрытии бара (`RiskMonitor._evaluate`), выход по сигналу —
  текущая цена кэша без проскальзывания (`_close_filled_position_locked`), уровни округляются до 10⁻⁸
  (`calc_sl_tp_prices`), а не до шага цены.
- Вход по close против open следующего бара (SBER, GAZP, LKOH, будни с 2025): 5m — медиана 0,008%, 99-й перцентиль
  0,10%; 1h — 0,003% / 0,36%; D — медиана 0,10%, 90-й 0,56%, 99-й 3,56%, максимум 10,3%.
- Стоп 1–2%: с гэпом через уровень 5–50% срабатываний; paper недоучитывает убыток на таком срабатывании в среднем на
  1,2–2,6%, до 4–9,4%.
- Дефекты backtrader (опыты в scratchpad):
  1. SL и TP в одном баре исполняются оба — фантомный шорт до сигнала выхода. На D таких дней 0,54% (SL 2% / TP 4%)
     и 3,43% (SL 1% / TP 2%).
  2. Бар входа не проверяется: SL/TP работают со следующего бара. Бар входа сам задевает SL 1% / 2%: D — 45% / 16%,
     1h — 2,1% / 0,26%, 5m — 0,11% / 0,01%. Другой исход у 35% / 9,5% D-сделок, бэктест лучше на 0,04–0,05 п.п.
     на сделку (около трети среднего результата); 1h — 1,3% / 0,2% сделок.
  3. Проскальзывание входа обрезается по high бара (продажи — по low), то есть использует ещё неизвестную цену:
     при 0,1% фактически 0,048% на 5m (обрезано 75% входов), 0,072% на 1h, 0,096% на D.
  4. Тейк исполняется по касанию ровно по уровню без проскальзывания; в real (C1) тейк — рыночная заявка после
     касания.
- Оба уровня в одном дневном баре: по 1h/5m первым был стоп в 20 из 28 разобранных дней (около 70%).

**Решение — договор исполнения.** Обязателен для paper и будущего движка (фаза 1–2 раздел «Единый движок»); backtrader до удаления
(B14) приводится к нему, где это возможно.

| Правило | Договор | backtrader до удаления |
|---|---|---|
| Сигнал | на закрытом баре | так же |
| Вход | первая цена нового бара (open) + проскальзывание, без обрезки по high/low | `slip_out=True` |
| Уровни SL/TP | от фактической цены входа; округление к шагу цены бумаги в сторону цены входа | округление в кодогене |
| Когда уровни начинают работать | сразу после входа, включая бар входа | вход и SL/TP отдельными приказами в `next_open`, проверка денег до отправки |
| Стоп | уровень − проскальзывание; если первая цена бара уже за уровнем (гэп) — эта цена − проскальзывание | так же (уже есть) |
| Тейк | касание → рыночное исполнение: уровень − проскальзывание; при гэпе — первая цена бара − проскальзывание | ровно по уровню — известное отличие, в эталоне помечается |
| Оба уровня в одном баре | стоп; в новом движке спорный бар разбирается по 1m (только такие бары) | стоп через `oco=` |
| Выход по сигналу | open нового бара − проскальзывание | так же (уже есть) |
| Часы | A5; **на баре аукциона открытия (будни 06:50–07:00, выходные — перед 10:00) не исполняется ничего** — вход и стоп по первой цене первого обычного бара (добавлено 2026-10-22, хвост A5) | A5, то же правило |
| Размер проскальзывания | B4 | параметр бэктеста |
| Размер позиции (добавлено с C4) | целые лоты (N лотов = N × размер лота акций); капитал на момент входа; для «риска на сделку» — стоп от фактической цены входа | исправить: сейчас лоты считаются штуками |
| Дивиденды (добавлено с B2) | цены обычные; право — позиция на закрытие последнего дня покупки; лонг + дивиденд × (1 − налог), шорт − дивиденд; деньги на баре гэпа | `broker.add_cash` в последнем баре последнего дня покупки |

- Знаки — для лонга; для шорта зеркально.
- В paper «первая цена бара» — open новой 1m-свечи стрима (C1: проверка на каждом обновлении); на 1m-барах это то
  же правило, что в бэктесте.
- Исполнение пользуется только тем, что известно в момент исполнения (поэтому нет обрезки по high/low).

**Самоконтроль.**
- **Договор в виде тестов.** Общий набор сценариев «бары → ожидаемые сделки»: гэп через стоп; оба уровня в баре;
  стоп в баре входа; тейк в баре входа; open = high бара входа; отказ во входе (нет денег — ни одного приказа, нет
  шорта); выход по сигналу; тейк гэпом. Один набор прогоняется через кодоген бэктеста и через paper (синтетический
  стрим), потом — через новый движок как приёмка фазы 1 (B14).
- **Журнал исполнений.** У каждой сделки paper, sandbox и real записываются цена по договору, фактическая цена,
  применённое правило (уровень, гэп, open, сигнал) и разница. Это данные для B4 и ранний сигнал расхождений.

**Где в коде Moex.**
- Бэктест: `app/strategy/ir_codegen.py` (`_gen_notify_order`, вход в `next_open`, `oco=`, округление уровней, проверка
  денег; в `next_open` читать только `open[0]` — там уже виден весь новый бар, см. B5); `app/backtest/engine.py:663` и `app/backtest/grid.py:423` — `bt.Cerebro(cheat_on_open=True)`,
  `broker.set_coo(True)`, `set_slippage_perc/fixed(..., slip_out=True)`.
- Paper: `app/trading/engine.py` (`_fill_paper_trade_locked` — первая цена нового бара + проскальзывание;
  `_close_filled_position_locked` — выход по сигналу с проскальзыванием); `app/trading/risk_monitor.py`
  (`calc_sl_tp_prices` — шаг цены; `_evaluate` — цена исполнения по договору; проверка внутри бара — путь C1);
  `app/trading/runtime.py` (первая цена нового бара в момент обработки сигнала).
- Журнал исполнений: поля сделки `LiveTrade` (цена по договору, правило), alembic-миграция; показ в карточке сделки.
- Тесты: общий набор сценариев договора (место — при реализации).

**Как проверяем.**
- D: вход 100,1, low бара входа 97, стоп 98,1 → бэктест и paper закрывают в баре входа по 98,1 − проскальзывание.
- 5m: open = high бара входа, проскальзывание 0,1% → цена входа open × 1,001 и в бэктесте, и в paper.
- Бар с high 105 и low 97 при SL 98 и TP 104 → исполнен стоп, тейк отменён, позиция 0.
- Тейк касанием 104 → paper 104 × (1 − проскальзывание); backtrader — 104, отличие помечено в эталоне.
- Денег на вход не хватает → ни входа, ни стопа, позиция 0.
- Сравнение бэктеста и paper на одних днях: доля D-сделок с другим исходом (35% при SL 1% сейчас) — ноль, кроме тейков
  (размер проскальзывания).

**Уточнения 2026-10-23 (проверка однозначности).**
- «Оба уровня в баре»: по 1m, если покрыты; иначе (и если оба уровня в одной 1m) — стоп. Такие бары — известное
  отличие в сверке бэктеста с paper и с эталоном, с причиной.
- Журнал исполнений — **отдельная таблица с этапа 2**: строка на каждое исполнение (тип, лоты, цена по договору,
  фактическая цена, правило, время), а не поля сделки — так её не придётся переделывать под частичные исполнения C1.

**Зависит от:** A1 (биржевые цены), A5 (часы), C1 (проверка внутри бара). **Влияет на:** B4 (размер проскальзывания,
данные журнала), B2, B14 (эталон снимается после правок B3), B10, B11, C3, C4.

#### B4. Проскальзывание в paper

*Этап:* 2 · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.**
- Paper проскальзывания не применяет: вход — close сигнального бара, выход — текущая цена кэша, SL/TP — ровно по
  уровню. `DEFAULT_SLIPPAGE_PCT = 0,05%` (`paper_engine.py:41`) стоит в `PaperBrokerAdapter.place_order`, который для
  сделок paper не вызывается. У сессии есть `commission_pct`, поля проскальзывания нет; у сделки есть пустой столбец
  `slippage`.
- Бэктест: в окне запуска по умолчанию 0,1% (`BacktestLaunchModal.tsx:82`), в API — 0 (`backtest/schemas.py:25`); из
  65 сохранённых бэктестов 55 с 0,1%, 10 с нулём. Окно grid search (`GridSearchForm.tsx`) проскальзывание и комиссию
  не передаёт — сервер берёт умолчания API: 0% и 0,05% (`backtest/schemas.py:124–125`); запуск бэктеста из ячейки
  тепловой карты — те же 0% и 0,05% жёстко (`GridSearchHeatmap.tsx:300`; уточнено 2026-10-21 при B8).
- Реальных исполнений 0; в песочнице 12, но выход записан ровно по цене сигнала — для калибровки не годится.
- Спред TQBR (снимок 21.10.2026 12:30 МСК, 484 бумаги, группы по обороту): топ-10 — медиана 0,013% (SBER 0,003%,
  GAZP 0,009%, LKOH 0,016%); 11–30 — 0,027%; 31–100 — 0,050%; остальные 384 — 0,326%. Для SBER 0,1% — около 65
  половин спреда; для половины малоликвидных бумаг 0,1% меньше половины спреда — результат завышен.

**Решение.**
- **Одно значение проскальзывания на все режимы стратегии**: бэктест, grid search и paper. Paper применяет его ко всем
  исполнениям по договору B3 (вход, выход по сигналу, стоп, тейк). Единицы — как в бэктесте (% или пункты).
- **Поле сессии «Проскальзывание»** рядом с комиссией. Заполняется из последнего бэктеста этой версии стратегии на той
  же бумаге и ТФ, иначе — 0,1%. Пользователь может изменить. Значение записывается в каждую сделку (`slippage`).
- **Grid search** берёт проскальзывание и комиссию из окна запуска. Умолчание одно для API и окна — 0,1% (одна
  константа).
- **Предупреждение по спреду.** При запуске бэктеста, grid и сессии терминал берёт текущий стакан бумаги (T-Invest);
  если половина спреда больше заданного проскальзывания — предупреждение «результат будет завышен, рекомендуем не
  меньше X%». Значение само не меняется. Биржа закрыта — «спред не проверен».
- **Калибровка — позже, по журналу исполнений B3**, только real (песочница не входит): по бумаге медиана и 90-й
  перцентиль фактического проскальзывания отдельно для входов, стопов, тейков и выходов по сигналу. Терминал показывает
  и предлагает значение, **без автозамены** — иначе старые и новые бэктесты несравнимы. Если стопы систематически хуже
  входов — отдельный параметр «проскальзывание стопов», решение по данным.

**Где в коде Moex.**
- `app/trading/models.py` (`TradingSession`: значение и единицы проскальзывания) + alembic-миграция; схема и роутер
  создания сессии (заполнение из последнего бэктеста версии, бумаги и ТФ).
- `app/trading/engine.py` (`_fill_paper_trade_locked`, `_close_filled_position_locked`), `app/trading/risk_monitor.py`
  (исполнение SL/TP) — проскальзывание по договору B3; запись в `LiveTrade.slippage`. Мёртвую константу
  `DEFAULT_SLIPPAGE_PCT` убрать.
- `frontend/.../GridSearchForm.tsx` (поля проскальзывания и комиссии, передача в запрос), `GridSearchHeatmap.tsx`
  (запуск из ячейки — значения сетки) и `app/backtest/grid.py` — значения из окна; `app/backtest/schemas.py` и
  `BacktestLaunchModal.tsx` — общее умолчание.
- Стакан: в адаптере T-Invest метода стакана нет — добавить (`GetOrderBook`); предупреждение во фронтенде окон запуска.
- Калибровка: отчёт по журналу исполнений (B3) в карточке бумаги или в настройках сессии.

**Как проверяем.**
- Paper: вход при первой цене бара 100 и проскальзывании 0,1% → 100,1; выход по сигналу при 105 → 104,895; стоп 98 →
  97,902; тейк 104 → 103,896.
- Сессия, запущенная после бэктеста с 0,2% на той же бумаге и ТФ, получает 0,2%; без бэктеста — 0,1%.
- Grid с 0,15% и комиссией 0,04% в окне — во всех прогонах сетки те же 0,15% и 0,04%.
- Бумага со спредом 0,6% при проскальзывании 0,1% → предупреждение «рекомендуем не меньше 0,3%»; SBER — без
  предупреждения.
- Сделки песочницы в калибровку не попадают.

**Зависит от:** B3 (договор исполнения, журнал исполнений). **Влияет на:** C3 (гейт качества сравнивает бэктест и
paper с одинаковыми издержками), C4.

#### B2. Дивиденды в бэктесте

*Этап:* 2 · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.**
- Влияние (SBER, 04.01.2024–14.10.2026, три выплаты, налог 13%): «купить и держать» по цене +4,2%, с дивидендами
  +37,7%. Лонги по 20 баров, вход на каждом баре: через отсечку 7,6% сделок, каждая занижена примерно на 10%,
  средняя сделка +0,18% против +0,93%; по 60 баров — +0,26% против +2,72%.
- Эталоны отчёта (`app/backtest/benchmark.py`) — тоже только по цене: за тот же период IMOEX −23,0%, MCFTRR (полная
  доходность нетто) −4,5%.
- **Гэп — в первую сессию после последнего дня покупки**, а не в дату реестра: SBER реестр пн 20.07.2026 → гэп
  в субботу 18.07; LKOH реестр 04.05.2026 → гэп в пятницу 01.05.
- **До 31.07.2023 — режим T+2**: SBER реестр 11.05.2023 → последний день покупки 08.05, гэп при открытии 10.05 (ISS:
  238,27 → 216,5 при дивиденде 25). T-Invest для старых выплат отдаёт `last_buy_date` по правилу T+1 (10.05) —
  неверно на день; по нему бэктест «купил» бы после падения и получил бы дивиденд (фантомные +10%).
- В журнале Moex нет двух выплат LKOH, которые есть в T-Invest: 397 ₽ (реестр 12.01.2026) и 256 ₽ (21.12.2022).

**Решение.**
- **Цены обычные** — для сигналов и прибыли, как в live (скорректированный ряд сломал бы договор B3: индикаторы видели
  бы не те цены, что live). Не реагировать на дивидендный гэп — фильтр событий B9 (`ctx.events`).
- **Право на дивиденд** — у позиции на закрытие последнего дня покупки. Последний день покупки считается по торговому
  календарю и режиму расчётов на дату сделки: T+2 для сделок до 31.07.2023, T+1 — с 31.07.2023 (последний торговый
  день, сделка которого рассчитывается не позже даты реестра). Сессии выходного дня последним днём покупки не считаются.
  `last_buy_date` T-Invest — только для сверки и только для выплат после 31.07.2023.
- **Сумма:** лонг получает дивиденд × (1 − налог), налог — параметр, по умолчанию 13%; шорт платит полный дивиденд.
  Paper — то же (сейчас начисляет без налога).
- **Когда:** деньги зачисляются на баре гэпа (первая сессия после последнего дня покупки) — без ложной просадки на
  кривой капитала; в бэктесте и в paper одинаково. Задержка фактической выплаты не моделируется.
- **Данные** — общий источник A4 (T-Invest + ручные поправки) для бэктеста и paper; неразобранные расхождения сверки
  в периоде — предупреждение в отчёте.
- **Отчёт бэктеста:** прибыль разделена на «от цены» и «дивиденды»; начисления — строками в списке сделок; эталоны —
  «купить и держать» с дивидендами (за вычетом налога) и индекс MCFTRR вместо IMOEX.
- **Сейчас в backtrader**, до снятия эталона B14; правило вошло строкой «Дивиденды» в договор исполнения B3 — новый
  движок обязан его соблюдать.

**Где в коде Moex.**
- Бэктест: `app/backtest/engine.py` и `grid.py` — расписание выплат (последний бар последнего дня покупки, сумма) из
  истории A4 передаётся в стратегию; `app/strategy/ir_codegen.py` — в `next()` на этом баре `broker.add_cash` по
  позиции (лонг × (1 − налог), шорт −); `app/backtest/metrics.py` — разделение прибыли; `app/backtest/benchmark.py` —
  «купить и держать» с дивидендами, MCFTRR (загрузка индекса как IMOEX сейчас); параметр налога — в схеме запуска.
- Paper и live: `app/corporate_actions/service.py` — `accrual_last_buy_date` с режимом T+2/T+1 по дате, сумма лонга за
  вычетом налога, зачисление в день гэпа; чтение выплат из истории A4.
- Общая функция «последний день покупки и бар гэпа» — одна для бэктеста и paper.

**Как проверяем.**
- SBER 2026: лонг, открытый в пятницу 17.07, получает 37,64 × 0,87 = 32,75 ₽ на акцию на баре субботы 18.07; открытый
  в субботу 18.07 — не получает; закрытый в субботу — получает.
- SBER 2023: последний день покупки 08.05, деньги на баре 10.05; позиция, купленная 10.05, дивиденда не получает.
- Шорт через отсечку LKOH 01.05.2026 — списание 278 ₽ на акцию.
- «Купить и держать» SBER 04.01.2024–14.10.2026 в отчёте — около +37,7%; эталон-индекс — MCFTRR.
- Paper и бэктест на одних днях с отсечкой — одинаковая сумма и одинаковый бар зачисления.
- Выплата, добавленная ручной поправкой A4 (PHOR 201 ₽), появляется в бэктесте.

**Зависит от:** A4 (источник выплат), B3 (договор исполнения). **Влияет на:** B9 (фильтр событий), B14 (эталон после
B2), E7 (сезонность), C3 (гейт качества).

### 3.4. Индикаторы и стратегии

#### Как хранятся стратегии, в том числе созданные ИИ

*Этап:* сводка правил — по этапам пунктов (фаза 1 — этап 3, фаза 2 — этап 4, режим «код» — потом)

**Факты.**
- Стратегия — запись в `strategies` (имя, статус, `current_version_id`); каждое сохранение — строка в
  `strategy_versions`: описание словами (`text_description`), блоки (`blocks_json`), сгенерированный код
  (`generated_code` — сейчас код backtrader), параметры (`parameters_json`), переписка с ИИ (`ai_chat_history`,
  `app/ai/chat_history.py`), автор, комментарий.
- БД: 102 версии у 4 стратегий; описание — у 43, сгенерированный код — у 97, переписка с ИИ — у 12; 98 версий с
  блоками, 1 — только с кодом `bt.Strategy`, 3 — без того и другого.
- Версии уже не перезаписываются (`app/strategy/service.py`): `create_version` создаёт новую (без дубля, если блоки и
  код те же в течение 5 мин), откат `restore_version` — новая версия-копия, есть именованные снимки. Сессия привязана
  к версии (`trading_sessions.strategy_version_id`), бэктест — тоже (`backtests.strategy_version_id`).
- Путь ИИ сейчас: чат → описание из 7 разделов → разбор в блоки (`strategy/block_parser.py`) → блоки → код для
  backtrader (`ir_codegen.py`) для бэктеста; live разбирает те же блоки своим исполнителем (`evaluator.py`) — два
  движка и две библиотеки индикаторов (`bt.indicators.*` и `strategy/indicators.py`): из 21 сверки сигналы совпали в 5.
- Режим ручного ввода кода стратегии в S8 удалён (не использовался); остаются блоки и генерация ИИ.

**Сводка правил.**
- **Канон версии — код** на Python против API `ctx` (одна библиотека `ta`); если версия собрана блоками, рядом хранятся
  блоки, а код генерируется из них. На этом коде работают бэктест, grid, paper, sandbox и real (фазы 1–2).
- **ИИ создаёт стратегию двумя путями:** блоками (описание → блоки, как сейчас) — с отчётом «что не перенеслось» (B12:
  «проблема» блокирует сохранение, «заметки» показываются); кодом против `ctx` — в режиме «код» (фаза 3).
- **Проверки до сохранения:** анализ кода до запуска (без импортов, файлов, сети; доступны только `ctx` и `math`);
  пробный запуск в отдельном процессе с лимитами времени и памяти; проверка «без заглядывания вперёд» (B5); проверка
  параметров по границам (B8).
- **Что хранится с версией:** код, блоки (если есть), описание, переписка с ИИ, отчёт B12, параметры с границами (B8),
  версии своих индикаторов, на которых версия прошла бэктест (B7), пометка «предложено ИИ» и карточка проверки правки
  (E11), автор и комментарий.
- **Каждое сохранение — новая версия;** сохранённая версия не меняется. Бэктесты и сессии ссылаются на конкретную
  версию; гейт C3 перед real проверяет именно её.
- **Правка от ИИ (E11)** — черновая версия «предложено ИИ» с карточкой проверки на скрытых данных; запущенные сессии
  остаются на своей версии, пока пользователь не переключит; для real новая версия заново проходит C3.
- **Свои индикаторы (B7)** хранятся отдельно у пользователя, тоже с версиями; изменённый индикатор действует в
  стратегии только после перепроверки бэктестом.
- **Миграция (B14):** 98 версий с блоками перегенерируются новым кодогеном; версия с кодом `bt.Strategy` переписывается
  вручную; старый `generated_code` и 65 бэктестов остаются в истории только для чтения.

**Где в коде Moex.**
- `app/strategy/models.py` (`StrategyVersion`): поле канонического кода против `ctx` (в фазе 1 вместо кода backtrader),
  отчёт B12, версии своих индикаторов, пометка «предложено ИИ» и ссылка на карточку проверки; alembic-миграция.
- `app/strategy/service.py` — создание версии с проверками до сохранения; `block_parser.py` — отчёт B12; новый
  кодоген блоков → код против `ctx` (фаза 1) вместо `ir_codegen.py`.
- `app/sandbox/` (`ast_analyzer.py`, `module_proxies.py`) — анализ кода и окружение только `ctx` и `math`; отдельный
  процесс с лимитами.
- `app/ai/` — запросы чата на создание стратегии блоками или кодом; переписка — в `ai_chat_history` версии.

**Как проверяем.**
- Стратегия, созданная ИИ, сохраняется новой версией с перепиской и отчётом B12; «проблема» в отчёте не даёт сохранить.
- Код с `import os` или чтением файла не сохраняется; заглядывающая стратегия не сохраняется (B5).
- Сохранённую версию нельзя изменить — правка создаёт новую; бэктест и сессия показывают номер своей версии.
- Изменение своего индикатора не меняет стратегию до перепроверки бэктестом.
- Правка от ИИ — черновая версия «предложено ИИ»; работающая сессия на прежней версии не изменилась; запуск real на
  новой версии требует допуска C3.

**Зависит от:** «Единый движок» (раздел «Единый движок»), B14, B12, B7, B8, B5, C3, E11.

#### B5. Проверка «без заглядывания вперёд»

*Этап:* 2 · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.**
- Проверка началом ряда (значения на полном ряде и на ряде без последних баров совпадают на общем отрезке): все 7
  индикаторов `strategy/indicators.py` проходят (SBER 1h, 12 377 баров, обрезки 1/10/100/500). Заведомо плохие
  пойманы: сглаживание по центру и `close[i+1]` — на обрезке 1 бар, «вершина ±5 баров» — только на обрезке 10.
- backtrader с `cheat_on_open`: в `next_open` уже виден весь новый бар (high, low, close) — ловушка для правки B3.
- T-Invest отдаёт формирующуюся свечу с `is_complete=False`, Moex признак не проверяет: свеча попадает в кэш и в
  бэктест (LKOH D 12.05.2026 в кэше close 5235 при итоговом 5271).
- Live считает на 200 последних свечах (`runtime.py:133`), бэктест — на всей истории без прогрева. EMA(200): разница
  значения медиана 0,24%, до 2,0%; сигнал «close выше EMA» расходится в 6,0% баров (EMA(100) — 1,3%, EMA(50) — 0,04%).
  Сейчас в блоках периоды не больше 50.

**Решение.**
- **Проверка началом ряда обязательна, на двух уровнях.**
  - Индикаторы: автотест библиотеки (`ta` фазы 0 и текущие `indicators.py`) на каждый индикатор — обрезки 1, 10, 100,
    500 баров и глубже наибольшего окна. Свои индикаторы (B7, этап 3) — при сохранении в песочнице; заглядывающий
    сохраняется с пометкой «перерисовывается» и недоступен стратегиям, блокам и алертам (исправлено 2026-10-23).
  - Стратегия целиком: бэктест на всём периоде и на периоде без последних K баров — сделки до точки обрезки
    совпадают. Ловит формулы, кодоген (`next_open`), старший ТФ, данные. Запуск: в тестах кодогена на эталонных
    версиях B14; при сохранении кода; условием гейта перед real (C3).
- **Одинаковый прогрев.** История live — не константа 200, а от стратегии: не меньше 5 × наибольший период индикатора,
  минимум 200 баров. Бэктест подгружает такой же прогрев до даты начала и торгует с даты начала. Контроль тем же
  инструментом: значение на окне прогрева против всей истории — разница меньше 0,01%.
- **Незакрытые бары** (`is_complete=False`) не попадают ни в кэш, ни в бэктест.
- **События и дивиденды — с даты объявления** (реализация в B9): стратегия в бэктесте видит событие только начиная с
  даты, когда о нём стало известно.
- Подгонка параметров (grid) — не B5, а квант-проверки C3.

**Где в коде Moex.**
- Тесты: `tests/unit/test_strategy/` — проверка началом ряда для каждого индикатора; общий помощник «проверка
  началом ряда» для стратегии (два прогона бэктеста) в `app/backtest/`; прогон на эталонных версиях B14.
- `app/strategy/ir_codegen.py` — в `next_open` только `open[0]` (B3).
- `app/trading/runtime.py` (`DEFAULT_HISTORY_SIZE`, `_preload_history`) — длина истории от стратегии;
  `app/backtest/engine.py` и `grid.py` — загрузка прогрева до `date_from`, сделки с `date_from`.

#### B8. Входы с типами и границами

*Этап:* 3 · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.**
- Moex: у параметров стратегии только имя и умолчание (`backtest/strategy_params.py` извлекает их из
  сгенерированного кода); сетка — список через запятую (`gridSearchUtils.ts`), до 5 параметров и 1 000 комбинаций.
  Границы полей блоков (период 1–500, отклонение 0,1–10) — только во фронтенде (`BlockDefinitions.ts`); сервер
  (`block_allowlist.py`) проверяет «число / значение из списка», диапазон — только у стопа и тейка (`RiskParams`).
- Опыт: сервер принимает в сетке `rsi_period` = 0, −5, 100 000 и 14,7; `stop_loss_pct` = −1 отклоняет.

**Решение.**
- **Одно описание параметра** — тип (целое, дробное, выбор, источник, время), умолчание, границы (от / до), шаг,
  подпись на русском. Где живёт: встроенные индикаторы — в библиотеке (B6); свои индикаторы — во входах (B7);
  стратегии в режиме «код» — в объявлении `params` (раздел «Единый движок») с типами и границами; блоки берут описание у индикатора.
- Из описания строятся: окно настройки (B6, B7); поля блоков, включая «Свой индикатор»; проверка на сервере; диапазоны
  grid search; соседние значения квант-проверок (C3) — в пределах границ; подсказка ИИ (не предлагает недопустимое).
- **Проверка на сервере на всех путях одинаково** (редактор, API, сетка, ИИ, запуск сессии) — как сейчас `RiskParams`
  для стопа и тейка; отказ с текстом вида «Период: целое от 2 до 200».
- **Grid search:** «от / до / шаг», заполненные вокруг текущего значения; список через запятую — второй способ; значения
  за границами не принимаются, целые остаются целыми; счётчик и лимиты (5 параметров, 1 000 комбинаций) — как сейчас.
- **Миграция:** 98 версий с блоками получают границы из описаний блоков; версия, написанная кодом, — тип по умолчанию
  (целое / дробное) и широкие границы; сохранённые бэктесты не меняются.
- **Когда** — в общем списке доработок (порядок — B1), вместе с `ta` (фаза 0), B6 и B7.

**Где в коде Moex.**
- Сервер: описание входов в библиотеке индикаторов; общая проверка параметров (обобщение `app/strategy/risk_params.py`)
  на путях `block_allowlist.py`, `backtest/grid.py` (`validate_grid_request`), `backtest/router.py`, создание сессии,
  `app/ai/`; `backtest/strategy_params.py` — отдавать описание (тип, границы, шаг, подпись), а не только умолчание.
- Фронтенд: `BlockDefinitions.ts` — поля из описания с сервера, а не константы; `GridSearchForm.tsx` и
  `gridSearchUtils.ts` — «от / до / шаг»; окна настройки B6/B7.
- Миграция данных версий стратегий (alembic).

**Как проверяем.**
- Сетка с `rsi_period` = 0, −5, 14,7 или 100 000 → отказ с текстом про границы; «от 10 до 30 шаг 5» → 5 значений.
- Блок RSI с периодом 600, присланный через API в обход редактора, → отказ на сервере.
- Окно настройки своего индикатора показывает поля по его описанию; значение за границей не применяется.
- Старая версия стратегии открывается и проходит бэктест с теми же результатами.

**Уточнения 2026-10-23 (проверка однозначности).**
- Границы у 98 старых версий читаются из описаний блоков на лету, версии не переписываются; значение вне границ —
  заметка B12.

**Зависит от:** B6, B7. **Влияет на:** C3 (квант-проверки), D2 (параметры алертов), E5 (скринер).

#### B12. Отчёт «что не перенеслось»

*Этап:* 3 (дефект тихих потерь — этап 1) · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.**
- Moex: разбор описания стратегии из 7 секций (выдаёт ИИ-чат) в блоки — `app/strategy/block_parser.py`
  (`TemplateParser.parse`); предупреждения (`warnings`) пользователь видит. Опыт на 4 описаниях:
  1. индикатор VWAP (нет в Moex) — предупреждение неверное по смыслу («ссылка [I2] не объявлена»), условие входа
     выброшено, остался только стоп;
  2. «выход: трейлинг-стоп 3% или прошло 10 баров» — **без предупреждения**, выход выброшен целиком;
  3. «RSI пересекает 30 снизу вверх И close > EMA 200» — **без предупреждения**, вход выброшен целиком;
  4. `MACD(…, line=histogram)` — **без предупреждения**, параметр отброшен, условие считается по линии MACD.

**Решение.**
- **Ничего не теряется молча:** каждая строка исходника либо переведена, либо попадает в отчёт.
- **Два уровня:** «проблема» — потерян смысл (условие, выход, индикатор): версия **не сохраняется**, пока часть не
  исправлена или явно не убрана; «заметка» — перенесено с изменением (умолчание, округление): показывается, не мешает.
- **Текст** — с номером строки, исходным фрагментом и подсказкой (что доступно, как обойти: убрать, режим «код»).
- **Отчёт хранится с версией стратегии** (история версий); ИИ-чат получает отчёт и может предложить исправленное
  описание.
- **Где действует:** разбор описания из ИИ-чата (сейчас); генерация своих индикаторов (B7) и стратегий ИИ; импорт Pine
  (фаза 4); новый кодоген блоков → код (фаза 1); перевод 98 старых версий на новый движок (B14).
- **Автотесты:** набор «непереводимых» примеров (четыре выше и новые) — каждый обязан дать проблему или заметку.

#### B13. Отложенное ТЗ по стратегиям

*Этап:* 4 (после фаз 1–2) · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.**

**Решение — 7 расширений блоков** (порядок по пользе):
1. **Линия индикатора** — любой выход (MACD сигнальная и гистограмма, Боллинджер верх и низ, Stochastic %D; у

3. **Пересечение с числом** («RSI пересекает 30 снизу вверх»).
4. **Источник индикатора** — hl2/hlc3/ohlc4 и «индикатор на индикаторе» (как в окне B6).
5. **Трейлинг-стоп** (% или ATR) — исполнение внутри бара по договору B3, как стоп.
6. **Выход по времени** (через N баров) — выход по open следующего бара (B3).
7. **Старший таймфрейм у индикатора** — значение после закрытия старшего бара (B5).
- Свой индикатор блоком — решено в B7. **Лонг + шорт в одной стратегии — остаётся отложенным** (решение 2026-10-17).

  местах. До этого отчёт B12 показывает «проблему: не поддерживается блоками — уберите или режим „код“».

  масштаба (осциллятор 0–100 и цена / ATR) — проверьте». Пользователю — пересмотреть версии 55–63 (фильтр не работает).

**Где в коде Moex.**

#### B9. Фильтр событий в стратегиях

*Этап:* 4 · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.**
- `GetAssetReports` (сырой gRPC, `instrument_id` = uid): у 15 крупных бумаг с 2018 года 536 отчётов, по годам
  2018–2021 — 93–108, 2022 — 54, **2023 — 8**, 2024 — 25, 2025 — 31, 2026 — 30; у LKOH и NLMK за 2023–2025 событий нет.
  Дата `created_at` раньше даты отчёта хотя бы на день — только у 6 из 536 (1%); обычно — день отчёта или запись
  задним числом (19.10.2022). Сейчас отчёт SBER 28.10.2026 известен с 21.10.2026.
- `GetDividends` (те же бумаги): 218 выплат, дата объявления есть у всех; от объявления до последнего дня покупки —
  медиана 11 дней, 10-й перцентиль 1 день; у 16 выплат объявление позже последнего дня покупки.
- «Цена» держать через отсечку при налоге 13% (B2): SBER 2026 — 4,89 ₽ ≈ 1,75% цены.

**Решение.**
- **API режима «код»:** `ctx.events.days_to(тип)`, `ctx.events.within(типы, before=N, after=M)`,
  `ctx.events.next(тип)` с данными события (для дивиденда — сумма и ожидаемый гэп в %). Типы: дивиденд, отчёт, ЦБ.
- **Блок «Фильтр событий»** (после движка фаз 1–2, как расширения B13): «не входить за N дней до / M дней после:
  отсечки / отчёта / ЦБ»; «закрыть позицию за N дней до отсечки».
- **«Известно с» (правило B5) по типам:** дивиденды — дата объявления (если она позже последнего дня покупки — событие
  в бэктесте до отсечки не видно, в отчёте это отмечается); ЦБ — расписание (известно за год); **отчёты — дата
  считается известной за K дней** до отчёта (параметр, по умолчанию 7), это допущение указывается в отчёте бэктеста.
  Фильтры «после события» точны всегда.
- **Покрытие:** если фильтр опирается на события, которых за период нет, отчёт бэктеста предупреждает («отчёты LKOH
  2023–2025: нет данных — фильтр по отчётам в этот период не работал»).
- **Ручные поправки отчётов** — тем же механизмом, что поправки дивидендов (A4): добавить, исключить, исправить дату.
- **Одна семантика в бэктесте и live** — общий движок (раздел «Единый движок») и хранилище событий D6.
- **Когда** — в общем списке, после движка фаз 1–2 и D6.

**Где в коде Moex.**
- Хранилище событий D6 + таблица ручных поправок отчётов (alembic); API `ctx.events` в движке (фазы 1–2); шаблон

#### B10. Импорт сигналов как данных

*Этап:* 4 · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.**
- Moex: импорта нет (сервер не принимает файлы); экспорт бэктеста в CSV/PDF есть.

**Решение.**
- **Сигналы — данные, а не код:** набор — тикер, часовой пояс, строки «время → позиция» (лонг / вне рынка / шорт),
  дата загрузки; имя и содержимое файла никогда не попадают в код.
- **Использование:** `ctx.signal` в режиме «код»; блок-условие **«Сигнал из файла»** в блоках, сочетается с остальными
  (стоп, фильтр событий B9 и т. д.) — после движка, как расширения B13.
- **Время по договору B3:** сигнал внутри бара — решение на закрытии этого бара, сделка — по open следующего бара с
  проскальзыванием.
- **Разбор под MOEX:** время по умолчанию — МСК (пояс настраивается); даты `ДД.ММ.ГГГГ` и `ГГГГММДД`, десятичная
  запятая, разделитель `;`, русские заголовки, сырой CSV из ISS; один тикер в файле; лимит размера.
- **Отчёт о разборе по B12:** нераспознанные строки, повторы времени, сигналы вне торговых часов (A5) — «проблемы»
  (с номером строки, блокируют загрузку) и «заметки».
- **Заглядывание (B5) проверить нельзя** — сигналы готовыми числами: бэктест помечается «сигналы рассчитаны вне
  терминала — проверка заглядывания невозможна»; такая стратегия **не проходит гейт перед real (C3)** — только для
  исследования; в торговлю — после переписывания правилом (блоки, код, свой индикатор B7).
- **Версии:** повторная загрузка — новая версия набора; бэктест запоминает версию.
- Торговля по внешним сигналам в live (входящий вебхук) — не здесь, отдельная тема.
- **Когда** — в общем списке, после движка фазы 1.

**Где в коде Moex.**
- Сервер: приём файла (`UploadFile`, лимит размера), разбор (форматы выше, пояс), модели «набор сигналов» и «версия»
  + alembic-миграция; источник `ctx.signal` в движке; шаблон блока «Сигнал из файла»; отметка в отчёте бэктеста и
  проверка в гейте C3.
- Фронтенд: загрузка файла, отчёт разбора, выбор набора в блоке и в окне бэктеста.

**Как проверяем.**
- SBER: сигналы SMA 50/200 из Python (файл в МСК) → те же сделки, что у стратегии со встроенными SMA (в эталонной проверке совпало 7 из 7).
- Файлы Финама, «русского Excel» и сырой CSV из ISS читаются; часовка 06:00 МСК остаётся 06:00 МСК.
- Имя файла с `U+2028` и кодом → сохраняется как текст, ничего не выполняется.
- Строка «32.13.2025;1» → «проблема» с номером строки, загрузка отклонена.
- Стратегия с блоком «Сигнал из файла» — пометка в отчёте бэктеста, запуск на real запрещён гейтом.

**Уточнения 2026-10-23 (проверка однозначности).**
- Вход — только при смене состояния сигнала (после стопа при том же «лонг» повторного входа нет); «вне часов» —
  заметка, сигнал относится к следующему бару; «проблема» — нераспознанная строка и повтор времени.

**Зависит от:** B3, B5, B12, фаза 1 раздел «Единый движок». **Влияет на:** C3.

#### B11. Сигнальный режим сессии

*Этап:* 4 · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.**
- разбор 06: сигнальный режим (стратегия live без брокера, сигналы — уведомлениями, как алерты стратегии TradingView)
  предлагался отдельным брокер-адаптером в фазе 2 раздел «Единый движок».
- Paper уже ведёт виртуальную позицию и публикует `trade.opened` в момент виртуального исполнения
  (`engine.py:4084–4099`: «Позиция открыта: стратегия: тикер направление N лот(ов) по цене ₽») и `trade.closed`
  (P&L). Текст — о свершившемся: нет уровней стопа и тейка, срока действия, обратной связи.
- Шум: из 2 294 уведомлений (18.05–19.10.2026) **1 892 (82%) — «Сессия восстановлена»**, до 462 за день (10.06);
  сделок — 29 открытий и 26 закрытий.

**Решение.**
- **Сигнальный режим — вид paper-сессии**, не новый движок: виртуальная позиция и исполнение по договору B3 и
  проскальзыванию B4, поэтому сигналы совпадают с бэктестом. Движка фазы 2 не требует.
- **Уведомление-указание** — новый тип «Сигнал стратегии» со своей настройкой каналов, Telegram первым: направление,
  тикер, стратегия, ориентир цены (первая цена нового бара), лоты по настройкам сессии, стоп и тейк (уровни и %),
  срок действия (до закрытия текущего бара). Стоп и тейк проверяются внутри бара (C1) и приходят срочным сигналом
  «СТОП: ПРОДАТЬ …».
- **«Исполнил / Пропустил» — только журнал:** виртуальная позиция идёт по стратегии и от ответа не меняется;
  «Исполнил» спрашивает фактическую цену — она пишется в журнал исполнений (B3) и служит данными о проскальзывании
  ручных сделок для калибровки B4.
- **Сгруппировать «Сессия восстановлена»:** после перезапуска — одно уведомление на все сессии («восстановлено N
  сессий»), а не по одному на сессию и перезапуск.
- Позже — тот же сигнал во внешнюю систему через вебхук (D5, блок 7).
- **Когда** — в общем списке доработок (порядок — B1), на текущем paper.

**Где в коде Moex.**
- Режим сессии: поле режима / признак «сигнальный» у paper-сессии (`app/trading/models.py`, схема и роутер создания
  сессии) + alembic-миграция.
- `app/notification/service.py` — тип «Сигнал стратегии» в `EVENT_MAP`, шаблон указания; `app/notification/telegram.py`
  и `telegram_webhook.py` — кнопки «Исполнил / Пропустил», ввод фактической цены; запись в журнал исполнений (B3).
- `app/trading/engine.py` — публикация сигнала при виртуальном входе и выходе (рядом с `trade.opened` / `trade.closed`),
  стоп и тейк — из пути C1.
- Группировка «Сессия восстановлена» — `app/main.py` (восстановление сессий при запуске) и публикация `session.recovered`.

**Как проверяем.**
- Сигнальная сессия SBER: при входе в Telegram приходит «СИГНАЛ: КУПИТЬ SBER … стоп … тейк … действителен до …»
  с кнопками; виртуальная позиция открыта по первой цене бара с проскальзыванием.
- «Пропустил» — позиция стратегии остаётся, выход по стратегии приходит сигналом «ПРОДАТЬ».
- «Исполнил» с ценой 293,60 при ориентире 293,45 — в журнале разница +0,05%.
- Касание стопа внутри бара — срочный сигнал «СТОП» сразу, не на закрытии бара.
- Перезапуск сервера с 5 сессиями — одно уведомление «восстановлено 5 сессий».

**Уточнения 2026-10-23 (проверка однозначности).**
- Делается после фазы 2 на `PaperBroker`; ручные исполнения входят в калибровку B4 отдельной категорией real; сигнал
  действует до закрытия бара входа.

**Зависит от:** B3, B4, C1. **Влияет на:** D5 (вебхук), C3.

### 3.6. Гейт качества и размер позиции

#### C3. Гейт качества перед real

*Этап:* 3 · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.**
- Moex: перед sandbox и real — только гейт сверки движков (`trading/service.py::_check_parity_gate`): любой бэктест
  версии со сверкой, на любом тикере и ТФ; расхождение снимается подтверждением с записью в аудит; результат не
  проверяется.
- 53 бэктеста: в плюсе 18; меньше 30 сделок — 32, ноль — 16; короче года — 20; сверка совпала в 5 из 21.
- Гейт сверки пропустил в sandbox: SBER — по бэктесту SBER D с 2 сделками; GAZP — 1h, месяц, 3 сделки, минус; GAZP,
  SBER, ZZZZ — по бэктесту MTSS 5m (−0,01%, расхождение сверки).

**Решение.**
- **Гейт качества — для real**; для sandbox и paper — та же карточка проверок, только для информации.
- **Бэктест допуска совпадает с сессией:** та же версия (и версии своих индикаторов, B7), тот же тикер и ТФ, те же
  издержки (B4), дивиденды (B2), договор исполнения (B3); период заканчивается не раньше месяца назад.
- **Проверки и пороги по умолчанию:**
  1. без заглядывания — проверка стратегии целиком (B5); нет импортированных сигналов (B10) и перерисовывающихся
     индикаторов — **жёсткий запрет, не обходится**;
  2. ≥ 30 сделок и ≥ 12 месяцев данных;
  3. вне выборки (walk-forward): доходность выше денежного рынка (фонд ликвидности LQDT) за тот же период — изменено
     2026-10-22 (хвост A5, было «Sharpe > 0»);
  4. стресс издержек: прибыль > 0 при комиссии ×2 и проскальзывании ×3 (не меньше 0,05% на сторону);
  5. соседние настройки в границах B8: ≥ 60% соседей не хуже половины результата;
  6. deflated Sharpe > 95% — число опробованных вариантов берётся из запусков grid search по версии;
  7. paper подтверждает бэктест: ≥ 10 сделок paper, сделки совпадают с бэктестом на тех же днях (B3, B11).
  Monte Carlo по сделкам — для информации (разброс просадок).
- **Карточка допуска** при запуске real: каждая проверка — значение, порог, ✔ / ✖; итог «допущена / не допущена».
- **Пороги — в настройках;** снижение пишется в аудит. Запуск без допуска — явное подтверждение, запись в аудит,
  пометка сессии «запущена без допуска»; проверка 1 не обходится.
- **Гейт сверки** остаётся до фазы 2 (после неё не нужен — раздел «Единый движок»).
- **Когда** — в общем списке, после B3, B4, B5.

**Где в коде Moex.**
- Новый модуль квант-проверок (`app/backtest/` — расчёт по результатам бэктеста и вариантам из grid; хранение
  результата проверки с бэктестом) + alembic-миграция.
- `app/trading/service.py` — гейт качества рядом с `_check_parity_gate` для `mode == "real"`, ошибка с карточкой,
  подтверждение и аудит (`app/common/audit.py`); пометка сессии.
- Настройки порогов (страница настроек риска) и аудит их изменений.
- Фронтенд: карточка допуска в окне запуска сессии и в результатах бэктеста.

**Как проверяем.**
- Сессия real по бэктесту другой бумаги или ТФ → «нет бэктеста допуска для SBER 1h».
- Бэктест с 2 сделками → ✖ «2 сделки из 30»; запуск только с подтверждением и записью в аудит.
- Стратегия с блоком «Сигнал из файла» или перерисовывающимся индикатором → запрет без возможности подтверждения.
- Порог «30 сделок» снижен до 20 — запись в аудите; карточка считает по новому порогу.
- Стратегия, прошедшая все 7 проверок, запускается на real без подтверждений.

**Уточнения 2026-10-23 (проверка однозначности).**
- Проверки вызывают бэктест **через интерфейс движка** (сквозное правило A6); у результата хранится, каким движком
  посчитан; допуск действует только по бэктесту текущего движка (после удаления backtrader — пересчёт). Части проверки
  1 про B10 и B11 добавляются на этапе 4. Гейт `tested` из «Единого движка» = допуск C3.
- Walk-forward — 5 окон, обучение 70% / тест 30%; сосед — ±1 шаг B8 по одному параметру, метрика — чистая прибыль, при
  ≤ 0 — ✖; пробы для deflated Sharpe — все версии на тикере и ТФ плюс правки E11; бэктест допуска — последний с теми
  же параметрами и размером позиции; стресс — проскальзывание max(3 × заданное, 0,05%).

**Зависит от:** B3, B4, B5, B8, B10, B11. **Влияет на:** C4.

#### C4. Размер позиции «риск на сделку»

*Этап:* 4 (дефект лотов — этап 1, до эталона B14) · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.**
- **Дефект: бэктест не знает размера лота.** В `app/backtest/*` и `ir_codegen.py` размер лота не используется:
  `fixed_lots` уходит в backtrader как число акций, `percent` — `int(cash × pct / 100 / close)` акций без округления
  до лота. Live считает лотами (`budget_per_lot`, `engine.py:1473`). Для бумаг с лотом 10 (GAZP, MTSS, GMKN) позиция
  бэктеста в 10 раз меньше, чем live; для AFKS (лот 100) — в 100 раз. Затронуты бэктесты GAZP (10) и MTSS (2).
- Лоты T-Invest: SBER 1, GAZP 10, LKOH 1, VTBR 1, MTSS 10, GMKN 10, AFKS 100, PLZL 1; в справочнике Moex у MTSS лот 1,
  синхронизации не было.
- Гэпы делают фактический убыток больше планового: через стоп — 5–50% срабатываний (B3), дивидендные — D6.

**Решение.**
- **Режим «Риск на сделку»:** лотов = свободный капитал × R% / (расстояние до стопа × размер лота), вниз до целого
  лота. Расстояние — от стопа стратегии: в % или «k × ATR(n)» (новый вид стопа в блоках, к расширениям B13); для
  трейлинга — начальное. Ограничения: не больше свободного капитала (без плеча) и лимита позиции Circuit Breaker;
  меньше 1 лота — сигнал пропускается с уведомлением (как сейчас).
- **Без стопа режим недоступен** — ошибка при сохранении (B8/B12); для real — опция в настройках риска «не входить без
  стопа» для любых режимов.
- **Одна формула в бэктесте и live** — строка «Размер позиции» в договоре исполнения B3: капитал на момент входа, цена
  — первая цена нового бара, стоп — от фактической цены входа.
- **План и факт риска:** отчёт бэктеста и журнал исполнений показывают плановый риск и фактический убыток по стопам
  (медиана, максимум), отдельно — гэпы.
- **Исправить лоты как дефект** (как C1, D1): бэктест считает в лотах («N лотов» = N × лот акций, «%» — с округлением
  до лота); размеры лотов сверяются с T-Invest (MTSS 1 → 10); бэктесты GAZP и MTSS пересчитать. **До снятия эталона
  B14.**
- **Когда** — в общем списке; дефект лотов — раньше эталона B14.

**Где в коде Moex.**
- `app/strategy/sizing.py` (формулы режимов, «риск на сделку»), `app/trading/engine.py` (`calculate_position_lots`,
  `budget_per_lot`), `app/strategy/ir_codegen.py` и `app/backtest/engine.py` (лот в бэктесте), `app/backtest/parity.py`
  и `router.py` (та же формула); схема сессии и блоков — новый режим и стоп в ATR; справочник инструментов —
  синхронизация `lot_size` из T-Invest.
- Отчёт бэктеста и журнал исполнений — «план / факт риска».

**Как проверяем.**
- Капитал 1 000 000 ₽, риск 1%: SBER 293,45 со стопом 2% → 1 703 лота; GAZP 112,41 со стопом 2% → 444 лота (4 440
  акций); стоп 5% → 177 лотов; стоп 0,5% у SBER → упор в капитал, фактический риск меньше 1%.
- Бэктест GAZP «5 лотов» → 50 акций, как в live.
- «%» на GAZP → целое число лотов (170 акций, а не 173).
- Режим «риск на сделку» без стопа — сохранение отклонено.
- MTSS в справочнике — лот 10.

**Уточнения 2026-10-23 (проверка однозначности).**
- Капитал = свободные деньги за вычетом комиссии входа; режим размера — параметр версии; для GAZP и MTSS — новые
  бэктесты, старые с пометкой «лоты штуками».

**Зависит от:** B3, C1, B8, B13. **Влияет на:** B14 (эталон после исправления лотов), C3.

### 3.7. Алерты и новости

*Этап:* 3 · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.**

**Решение.**
- **Формат — язык условий стратегий** (то же дерево, в которое собираются блоки): сравнение, пересечение (вверх /
  вниз / любое), «в зоне», И / ИЛИ / НЕ. Операнды — по B6, B7, B13: поля цены (open, high, low, close, hl2, hlc3,

  линии; параметры — с границами B8. Нарисованная линия — D4.
- **Исполнитель — модуль условий фазы 0** (вместе с библиотекой `ta`), вызываемый отдельно от стратегии, без позиции
  и брокера. На нынешнем `evaluator.py` не делаем (8 индикаторов, нет цены, одна линия — пришлось бы переделывать).
  Алерты — **первый потребитель** модуля: библиотека проверяется на живых данных раньше, чем на неё перейдут стратегии
  (фазы 1–2); довод для порядка работ в B1.
- **Редактор в окне алерта** — строки «что — как — с чем», до 5, «все / любое»; хранится деревом, вложенную логику
  можно добавить без миграции. Вид — по двум макетам при реализации.
- **Повтор:** «Один раз»; **«Каждый раз, когда условие становится истинным» — по умолчанию**; «Каждый бар, пока
  истинно» — с предупреждением о частоте. Переходы считаются с момента создания (как сторона уровня в D1): истинное
  при создании условие ждёт нового перехода. «В зоне» в режиме «при переходе» = «вошёл в зону».
- **Предпросмотр по истории при создании:** тот же исполнитель прогоняет условие по прошлым барам — «сработал бы ≈ N
  раз в день» и метки на графике.
- **Проверка:** одна подписка 1m на бумагу (общая с ценовыми алертами и графиками); бары ТФ — из 1m агрегатором
  (решение 3), только биржевые (A1); момент закрытия бара — по D3; буфер баров «бумага + ТФ» общий для алертов; после
  перезапуска состояние восстанавливается по истории, переход за время простоя приходит с пометкой «с опозданием».
- **Срабатывание** — атомарно, как сейчас (отметка + уведомление + outbox). Текст по умолчанию со значениями
  операндов («LKOH 5m: RSI(14) пересёк вверх 70 → 71,3; цена 6 117,5 ₽»), свой текст с подстановками; история
  срабатываний (время, бар, цена, значения, статус доставки); изменение, пауза, перезапуск.
- **Один список «Алерты»** для двух видов — «уровень» (D1, внутри бара по high/low) и «условие» (D2, на закрытии бара);
  одна таблица (в `price_alerts` 0 строк — переносить нечего), общие история, текст, повтор, лимиты.
- **Откуда создать:** кнопка на графике; пункт «Алерт…» в легенде индикатора — с подставленным индикатором и
  параметрами.
- **Лимиты:** до 100 бумаг с алертами (каждая — одна из 300 подписок) и до 200 активных алертов; значения — в
  настройках.
  Уведомления скрина (E1, часть 3) в этот лимит не входят: они считаются по закрытым дневкам из кэша и подписок на
  поток не держат (уточнено сверкой 2026-10-22).
- **Перерисовывающиеся индикаторы** (B6: Zig Zag и др.) в алертах недоступны, как в стратегиях: предпросмотр показал
  бы сигналы, которых в live не будет.
- Не в D2: закрытый / формирующийся бар — D3; линия — D4; вебхук — D5; один алерт на много бумаг — алерты скринера
  (блок 8).

#### D3. По умолчанию — закрытый бар

*Этап:* 3 (закрытие бара по расписанию — с решением 3, этап 1) · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.**
- Опоздание «по следующему бару» (кэш 5m LKOH, GAZP, MTSS с 2026-04-01): 5m — вовремя 96–98%, на 5–60 мин позже
  1,3–3,6% (минуты без сделок, перерывы); 1h — последний бар дня (5,2–5,4% баров) на 6–7 ч; **D — все бары на
  7 ч 05 мин** (первая свеча следующего дня — 06:55).
- T-Invest с `waiting_close=True` присылает закрытую свечу через 0,14–0,22 с после конца периода (1m, 5m; SBER, AFLT,
  MSTT), в том числе без сделок в конце периода; минута совсем без сделок свечи не даёт. Поток без флага (как в Moex):
  следующий бар виден через 0,5 с у SBER, 3,1 с у AFLT (медиана), у MSTT — только со следующей сделкой.
- Формирующийся бар против закрытого (LKOH 1h из 5m, год; сигнал — переход в истину): RSI(14) > 70 — 130 сигналов,
  53 (41%) не дожили до закрытия, опережение доживших — медиана 30 мин; close > SMA(50) — 206, 79 (38%), 35 мин;
  close выше верхней полосы Боллинджера(20, 2) — 190, 58 (31%), 25 мин.

**Решение.**
- **Принцип:** условия по индикаторам (алерты D2, скринер E5, сигналы B11; стратегии — уже B5) проверяются на
  **закрытом баре**. Касания цены (уровень D1, стоп и тейк C1) — внутри бара: это свершившийся факт, а значение
  индикатора до закрытия — оценка, которая меняется.
- **Формирующийся бар — только явным выбором** («проверять до закрытия бара») с предупреждением «≈ 3–4 из 10 таких
  сигналов исчезают к закрытию»; не чаще раза на бар; если к закрытию условие ложно — пометка «не подтвердился» в
  истории (в приложении, без повторной отправки во внешние каналы).
- **Закрытие бара — по времени, а не по следующему бару:** бары ТФ собираются из закрытых минутных свечей T-Invest
  (`waiting_close`); бар закрыт в конце своего периода, последний бар дня — в конце торгов по расписанию бумаги (A5:
  23:50 в будни, 19:00 у бумаг с выходными торгами); таймер ждёт опоздавшие свечи 2 с; минута без сделок закрытие не
  задерживает.
- **Опоздавшая минута** (пришла после таймера) — бар пересчитывается, в истории алерта «бар уточнён», без повторной
  отправки (уточнение 2026-10-22).
- **Неполный бар** (обрыв стрима, `bar_complete=False`) не проверяется, как у сессий; в истории алерта — «бар пропущен:
  неполные данные».
- **Сессии стратегий — без изменений:** решение на закрытом баре, вход по первой цене следующего (договор B3).
- **Скринер (E5)** — тот же принцип: по умолчанию последний закрытый бар, формирующийся — переключателем с пометкой.
- **График** показывает формирующийся бар и индикаторы по нему, как сейчас (отображение, а не сигнал); метки алертов и
  предпросмотра — по закрытым барам.
- **Когда** — в общем списке доработок (порядок — B1), вместе с D2 и агрегатором решения 3.

**Где в коде Moex.**
- `app/market_data/stream_manager.py` (`_AggregatingCandle`, агрегатор решения 3) — закрытие периода по расписанию

- `app/broker/tinvest/multiplexer.py` — подписка закрытых минут (`waiting_close=True`) отдельным маршрутом рядом с

- Монитор алертов (D2) — подписка на «бар ТФ закрыт»; поле алерта «режим бара» (закрытый / формирующийся), пометка

**Как проверяем.**

**Проверено (запись стрима T-Invest 21.10 17:23–00:00 МСК; SBER, AFLT, MSTT; обрывов 0).**

#### D4. Алерт от трендовой линии

*Этап:* 3 · *Статус:* ✅ делаем (принято 2026-10-21)

**Факты.**
- Moex: трендовая — отрезок; точки можно перетаскивать; Lightweight Charts ставит бары через равные промежутки, поэтому
  линия на графике прямая **по номерам баров** на всех ТФ. Точка правее последнего бара переводится во время шагом ТФ
  без учёта ночей (`seqTimeForIndex`) — после ночи она оказывается на другом баре. В `chart_drawings` 3 линии SBER
  старого формата.
- Время против баров (поддержки через соседние минимумы): пробой на другом баре или только при одном способе —
  LKOH 1h **58%** (149 линий; расхождение цены через 60 баров — медиана 1,47%, 90% 5,4%), SBER D 24%, GAZP 5m 17%.
  Пример LKOH 1h: точки 07.03.2025 17:00 7100,5 и 10.03.2025 11:00 7172,5 — по барам пробой 10.03 17:00 (close 7187,0
  < 7208,5), по времени линия там 7179,0, пробой лишь в 20:00.
- Бары по факту против слотов расписания (5m): пропущено 0,4–2,3% слотов, пробой на другом баре у 0,1–0,5% линий.
- Касание (low ≤ линии) и закрытие за линией (close < линии) совпадают на одном баре в 29–30%; в 70% — касание без
  пробоя закрытием (отскок или пробой позже, медиана через 3–4 бара).

**Решение.**
- **Цена линии — по номеру бара**, как её рисует график: p1 + (p2 − p1) × (k − k1) / (k2 − k1); номер — по барам
  основного ряда (A1: дилерские не считаются, торги выходного дня у бумаг с `weekend_flag` — считаются). Не по времени.
- **ТФ линии** = ТФ проверки алерта; при видимости рисунков на всех ТФ (E8) выбирается при создании (по умолчанию — ТФ
  открытого графика); линия на графике этого ТФ — та, что проверяет алерт.
- **Два режима:** «Касание линии» (по умолчанию) — как D1, внутри бара по high/low, направление по цене при создании,
  гэп с пометкой (цена линии на текущем баре известна заранее — это касание цены, принцип D3); «Закрытие за линией» —
  на закрытом баре (D3), условие D2 с операндом «линия».
- **Отрезок продолжается вправо:** алерт от трендовой следит за продолжением после второй точки; пока алерт активен,
  продолжение рисуется пунктиром. Луч и продлённая — E9.
- **Алерт привязан к рисунку, а не к копии:** перетащили точку — алерт пересчитывает линию и направление (в истории —
  «линия изменена»); удаление линии с алертом — с подтверждением, алерт удаляется вместе; на линии — колокольчик.
- **Обе точки — на барах:** точка правее последнего бара — алерт недоступен, подсказка «поставьте обе точки на свечи».
- **Горизонтальный уровень** (рисунок) → алерт D1. История, текст, каналы, лимиты — общие с D2.
- **Когда** — в общем списке доработок (порядок — B1), вместе с D2.

**Где в коде Moex.**
- `app/chart_drawings/` (модель, роутер) — связь рисунка с алертом, удаление с подтверждением.
- Модель `Alert` (D2): вид «линия» — ссылка на рисунок, ТФ, режим (касание / закрытие), направление при создании.
- Монитор алертов: одна функция «цена линии на баре» по барам ТФ (агрегатор решения 3); она же для предпросмотра.
- Фронтенд: пункт «Алерт от линии» в меню рисунка (`DrawingsLayer.tsx`), пунктир продолжения и колокольчик
  (`TrendlinePrimitive.ts`), предупреждения при перетаскивании и удалении.

**Как проверяем.**
- Линия LKOH 1h из примера: «закрытие за линией» срабатывает 10.03 17:00, где пробой виден на графике, а не в 20:00.
- Касание без закрытия за линией: «касание» срабатывает, «закрытие» — нет.
- Перетащили точку → новая цена линии в алерте; удаление линии с алертом — подтверждение.
- Дилерские свечи выходных не сдвигают номер бара.
- Точка правее последнего бара → алерт недоступен.
- Цена линии сервера на последнем баре = цене линии на графике (тест-сверка).

**Уточнения 2026-10-23 (проверка однозначности).**
- Вид `line` в общей модели алертов (A3). Алерты от лучей, продлённой линии и горизонтального луча (E9) делаются
  здесь. Точка рисунка вне баров ТФ проверки — первый бар после её времени; формирующийся бар = «правее последнего
  бара».

**Зависит от:** D1, D2, D3, A1, A5, решение 3. **Влияет на:** E8 (ТФ линии в алерте), E9 (луч, продлённая, канал —
операнды алерта).

#### D5. Исходящий вебхук

*Этап:* повтор доставки — этап 1 (дефект); вебхук — отложено · *Статус:* ⏸ отложено (решено 2026-10-21); повтор доставки Telegram и почты — ✅ как дефект

**Факты.**
- Moex: каналы — приложение, Telegram (свой бот, 3 попытки за ~3 с, `notification/telegram.py`), почта; настройки по
  17 типам событий. **Outbox повторяет недоставленный канал только при старте сервера** (`main.py:183`,
  `replay_pending_events`) и только для строк возрастом 1 с – 1 ч (`common/outbox.py`, `OUTBOX_REPLAY_*`);
  периодического повтора нет — при сбое Telegram дольше ~3 с без перезапуска в течение часа сообщение теряется.
- Логи 24.06–21.10.2026 (`logs/dev.log`): 24 отправки в Telegram, 0 повторов, 0 сбоев — на практике пока не
  проявлялось. Провалы доставки (июль, 15–19.10) — намеренное подавление DEV_MODE на стенде.

**Решение.**
- **Вебхук — отложен.** Вернуться, когда появится конкретный получатель. Требования на будущее остаются в разбор 06
  и проверке выше: только https с проверкой сертификата; адрес проверяется после разрешения имени (запрет loopback,
  частных сетей, link-local, 0.0.0.0, IPv4 внутри IPv6), соединение — на проверенный адрес, без редиректов; подпись
  HMAC, `event_id` и время; минимальное тело без настроек и адресов; адрес хранится зашифрованным; повтор с паузами.
- **Повтор доставки Telegram и почты — исправить как дефект** (низкая срочность; важно для алертов D2–D4 в Telegram):
  общий фоновый повтор недоставленных каналов outbox по расписанию (например через 10 с, 1 мин, 5 мин, 30 мин), а не
  только при старте; уже доставленные каналы не дублируются (как сейчас `data.delivered`); после последней неудачи —
  отметка «не доставлено» в уведомлении, видимая в приложении.
- **Когда** — в общем списке доработок (порядок — B1).

**Где в коде Moex.**
- `app/common/outbox.py` (`load_replayable`, окна возраста), `app/notification/service.py` (`_deliver_outbox`,
  `replay_pending_events`) — фоновый повтор по расписанию; задание в `app/scheduler/service.py`.
- `app/notification/models.py` / схема — статус «не доставлено» по каналу; отображение в списке уведомлений.

**Как проверяем.**
- Telegram недоступен 10 минут (заглушка нотификатора) → сообщение доставлено повтором без перезапуска сервера, один раз.

#### D7. Новости

*Этап:* параллельная дорожка (сборщик и архив — этап 1) · *Статус:* ✅ делаем (принято 2026-10-21, со второго захода)

**Факты.**
- Биржа (ISS sitenews, 500 сообщений за 22 дня, 90 пар «сообщение — акция», 39 бумаг): сообщения **запаздывают** за
  ценой — «дискретный аукцион» (5): за час до +5…+19%, после −3…+0,5%; расширение верхней границы коридора (10):
  медиана до +1,26%, после −1,45%; РЕПО и ставки переноса (44) — шум. Фон: «заметных» (> 2× медианы) часов — 25%.

- Реакция на новости СМИ (25 пар, 19–21.10): **заметное движение за час ДО публикации — 64%, ПОСЛЕ — 20%** (фон 25%);
  после — например OZON «плата для владельцев ПВЗ» −1,15% (обычно ±0,23%), SPBE −1,14%, ALRS «СД рассмотрит
  дивполитику» −0,86%. Выборка мала — вывод предварительный.
- Идеи T-Invest (SignalService, 10 231 сигнал с 2024 года, 201 бумага): аналитики брокеров и «Автослед» (2 716) — в плюс
  46%, лучше индекса за те же дни 49%, до цели 15%, срок — медиана 16 дней; разброс источников 33–54% (Финам 54%,
  БКС 53%, АКБФ 33%); технические (7 515) — 43% / 44%.

**Решение.**

  сообщения биржи ISS по всему рынку; ЦБ — когда сайт доступен (заседания — D6); идеи аналитиков T-Invest. Не берём:
  e-disclosure (закрыт для программ), зарубежные ленты.
- **Свой архив с первого дня:** заголовок, ссылка, источник, время публикации и **время получения**, привязка к бумагам;
  без текста статьи (авторское право). ≈ 300–500 новостей в день. Причина: ленты хранят часы, прошлое не скачать.
- **Привязка ко всем акциям TQBR:** словарь (короткие названия ISS + ручные псевдонимы + исключения общих слов);
  точнее — ИИ-разметка (D8).
- **Где видно:** лента «Новости» с фильтрами (бумага, источник, тип — список D8: отчёт, дивиденды, сделка, санкции, регулятор, менеджмент, биржа, прочее);
  **метки на графике** в момент публикации; карточка бумаги и календарь D6.
- **Реакция рядом с новостью:** «за час до: +2,3%, после: −0,3%» — видно, отыграна ли новость.
- **Алерт «новость по бумаге»** — по списку бумаг или всему рынку, с фильтром слов; каналы — как у алертов D2.
- **Идеи аналитиков T-Invest — со статистикой источника** (доля в плюс, медианный результат за 2024–2026).
- **Новости в стратегиях (`ctx.news`) — позже**, когда накопится архив (6–12 мес.) и будет разметка D8; «известно с» =
  время получения (B5).
- **Контрольная точка через 1–3 месяца:** повторить замер «до / после» на 500+ новостях архива по источникам.
- **Когда** — в общем списке доработок (порядок — B1); сборщик и архив — как можно раньше (история копится только с
  момента запуска).

**Где в коде Moex.**
- Новый модуль `app/news/`: новости, связи «новость — бумага», источники, таблица псевдонимов; alembic-миграция;
  сборщик — задание раз в 1–2 мин в `app/scheduler/service.py`; реакция — по свечам кэша или ISS.
- `app/notification/service.py` — тип «Новость по бумаге».
- Адаптер T-Invest — `GetSignals` / `GetStrategies`; ночной пересчёт статистики источников.
- Фронтенд: страница или панель «Новости», метки на `CandlestickChart.tsx`, карточка бумаги.

**Как проверяем.**

**Уточнения 2026-10-23 (проверка однозначности).**

- Реакция «до / после» — по 1m ISS от времени публикации, считается, когда закрылся час «после» плюс 15 мин; нет

#### D8. ИИ-разметка новостей

*Этап:* параллельная дорожка, вместе с D7 · *Статус:* ✅ делаем вместе с D7 (принято 2026-10-22; в пакете было «не сейчас»)

**Факты.**
- Эталон — 108 заголовков RSS 19–21.10 с ручной разметкой (`d8_news_labels.json` (приложение 6.1)). Словарь: нашёл бумагу в
  48, **верно в 35 (73%)**; 13 ложных — общие слова («система» ×7, «вклады» → VKCO, «Вкусвилл», «Мосбиржа» как
  площадка или индекс ×4, ISIN облигации). Из 36 заголовков о компаниях нашёл 35; пропуск — косвенная связь («Титов:
  спрос на игристое» → ABRD). Новости о рынке целиком (17) и об отрасли (4) словарь не видит; 51 — не про рынок.
- Тональность против реакции цены (25 пар): **до** публикации цена шла в сторону новости в 7 из 10 однозначных
  случаев; заметных движений **после** — 4: совпало 1 (GAZP +0,73%), наоборот 1 (SPBE −1,14% при «+»), неоднозначно 2
  (OZON «плата для ПВЗ» −1,15%, ALRS «дивполитика» −0,86%). Тональность — подпись к новости, а не сигнал.
- Стоимость (OpenRouter, 21.10.2026): Qwen3.8 Flash $0,15 / $0,47 за 1 млн входных / выходных токенов, DeepSeek V4 Pro —
  от $0,43 / $0,86. 500 новостей в день пачками по 20 ≈ 100 тыс. входных + 20 тыс. выходных токенов в день → **≈ $0,7
  в месяц** (Qwen Flash) или ≈ $1,8 (DeepSeek Pro); с запасом ×3 на кириллицу — меньше $6.

**Решение.**
- **Что размечает ИИ:** бумаги — **только из переданного списка TQBR** (ответ по схеме JSON, тикер вне списка
  отбрасывается); охват — компания / отрасль / весь рынок; тип — отчёт, дивиденды, сделка, санкции, регулятор,
  менеджмент, биржа, прочее; тональность для компании — + / − / 0 / «неоднозначно»; важность 1–3.
- **Словарь остаётся:** мгновенная привязка и запасной путь, если ИИ недоступен или исчерпан лимит. Храним обе разметки;
  в ленте видно, кто разметил (словарь или ИИ, модель и версия подсказки).
- **Тональность — «оценка ИИ», не сигнал:** показывается рядом с реакцией «до / после» (D7); в `ctx.news` — только после
  проверки на архиве (контрольная точка D7, 1–3 месяца).
- **Ключ и модель:** настройка «провайдер для фоновых задач» (по умолчанию — активный провайдер владельца, сейчас Qwen3.8
  Flash), дневной лимит токенов; цены моделей вносятся в настройки — расход виден в Moex. В модель уходят только
  публичные заголовки, данные счёта и позиций — нет.
- **Проверка модели перед включением** — на эталоне 108 заголовков: верная бумага ≥ 95% (у словаря 73%), ни одного
  тикера вне списка. Эталон размечен моделью уровня Claude; дешёвая модель может ошибаться чаще — тогда другая модель
  или словарь.
- **Задержка:** разметка — секунды (замерить при реализации); алерт «новость по бумаге» (D7) ждёт её не дольше ~10 с,
  иначе идёт по словарю с пометкой. Фильтры алерта — по типу и тональности.
- **Когда** — в общем списке доработок вместе с D7 (порядок — B1).

**Где в коде Moex.**
- `app/news/` (D7) — шаг разметки после сборщика: пачки по 20, подсказка со списком TQBR, проверка ответа (JSON,
  тикеры из списка), поля разметки, модель и версия подсказки; повтор при сбое, затем словарь.
- `app/ai/` — вызов провайдера вне чата, настройка «провайдер для фоновых задач», учёт токенов в `ai_usage_daily`,
  лимиты.
- Фронтенд — фильтры по типу и тональности в ленте и алерте, значок «ИИ / словарь», выбор провайдера в настройках ИИ.

**Как проверяем.**
- Эталон: бумаги верны ≥ 95%; «система» и «вклады» не привязываются; «Титов: игристое» → ABRD; тикеров вне TQBR нет.
- ИИ недоступен или лимит исчерпан → разметка словарём с пометкой, лента и алерты работают.
- Расход токенов за день виден в настройках ИИ.
- Алерт «ALRS, тип = дивиденды» срабатывает по разметке ИИ.

**Уточнения 2026-10-23 (проверка однозначности).**
- Провайдер для фоновых задач выбирает владелец (как «счёт для рыночных данных», A8).

**Зависит от:** D7, модуль `app/ai`. **Влияет на:** алерты по новостям (D7), `ctx.news` (позже), скринер (E-блок).

#### E11. Реплей, пошаговый разбор стратегии и ИИ-помощник

*Этап:* реплей графика — после фазы 0 (этап 2); реплей стратегии — после сверки фазы 1 (этап 3); ИИ-разбор — этап 4 · *Статус:* ✅ делаем (принято 2026-10-22, со второго варианта)

**Факты.**
- Moex: ручной торговли нет (в ФТ — только ручное закрытие); 102 версии у 4 стратегий, 65 бэктестов. `backtest_trades`
  хранит сделки, значения условий по барам не хранятся (пересчёт — модуль условий D2, 81 тыс. баров за 133 мс). ИИ
  (`app/ai`) по `/backtest` видит только метрики, сделок и баров не видит, бэктест не запускает.
- Опыт «поправить стратегию под убыточные сделки» (103 ликвидные бумаги, 1h ISS с апреля; лонг по RSI(14), лучший из
  27 фильтров на первых 60% баров): убыточных 1 830 → 650, прирост — медиана **+16,6 п.п. на истории, +1,3 п.п. на новых
  данных**; помогла у 62% бумаг, навредила у 34%. Лучшая общая правка оставляет 122 сделки из 3 967.

**Решение.**
- **Часть 1 — реплей графика** на любой панели (G1): точка в прошлом, правее скрыто; шаг, проигрывание 0,5–10×,
  синхронно на панелях бумаги; индикаторы только по видимым барам (B5). **Учебная торговля в реплее:** «Купить»,
  «Продать», «Закрыть», стоп и тейк, лоты, проверка денег, исполнение по договору B3; свои итоги, отдельно от сессий.
  Ручной тикет вне реплея — нет.
- **Часть 2 — реплей стратегии:** пошаговый разбор бэктеста — шаг по барам и переход к следующему сигналу или сделке;
  на баре — каждое условие стратегии со значением и ✔ / ✖ (что разрешило или запретило вход и выход), капитал и позиция;
  сделки реплея совпадают с бэктестом (тот же движок, B3).
- **Часть 3 — ИИ-разбор** (по кнопке, провайдер пользователя):
  - «Почему эта сделка» — значения условий, индикаторов, время, волатильность, объём, события дня (D6, D7);
  - «Как улучшить стратегию» — Moex считает таблицу «прибыльные против убыточных» по признакам; ИИ получает её и
    сделки **только первых 70% периода**; предлагает 2–3 правки как изменения блоков (фильтр, параметр в границах B8,
    выход) по схеме, без кода;
  - **каждая правка проверяется автоматически:** скрытые 30%, весь период, другие ликвидные бумаги, сравнение со
    случайным отказом от того же числа сделок; карточка с итогом «подтвердилась / не подтвердилась»;
  - применение — кнопкой, как новая черновая версия с пометкой «предложено ИИ»; сессии не меняются;
  - каждая проверенная правка — опробованный вариант для deflated Sharpe (C3).
- Стоимость: 100 сделок × ~20 признаков ≈ 15 тыс. токенов ≈ $0,003 на запрос (Qwen3.8 Flash); данных счёта в запросе нет.
- **Когда** — сразу в общем списке; порядок (B1): реплей графика — независим; реплей стратегии — после модуля условий D2
  и B3; ИИ-разбор — после реплея стратегии и C3.

**Где в коде Moex.**
- Фронтенд: режим реплея в `CandlestickChart` и `ChartPage` (панели G1), учебные кнопки, панель «Условия на баре»,
  карточки правок.
- `app/backtest/`: прогон версии по барам со значениями условий, таблица «прибыльные против убыточных», проверка правки
  (скрытые 30%, весь период, другие бумаги, случайный отказ), учёт проб для C3.
- `app/ai/`: два запроса с подсказкой и схемой ответа «изменения блоков» (как D8), без доступа к скрытому периоду.
- `strategy`: черновая версия с пометкой «предложено ИИ».

**Как проверяем.**
- Реплей SBER 1h с 01.09: правее курсора баров нет, RSI на последнем видимом баре — как в тот момент.
- Учебная покупка в реплее при гэпе — по договору B3.
- Реплей бэктеста даёт те же сделки, что бэктест; на баре без входа видно, какое условие запретило вход.
- ИИ-запрос не содержит сделок последних 30% (журнал запроса).
- Правка, хорошая только на первых 70%, — «✖ не подтвердилась».
- Принятая правка — новая черновая версия, сессии не изменились.

**Уточнения 2026-10-23 (проверка однозначности).**
- **Порядок изменён** (сквозное правило A5): реплей графика — **после фазы 0**: учебные заявки исполняет серверный
  SimBroker (комиссия и проскальзывание — как в бэктесте); индикаторы в реплее — с B6 (расчёт «до времени T»); старшие
  ТФ — формирующийся бар из 1m; **реплей стратегии — после сверки фазы 1 с эталоном**.
- Учебная торговля: стартовый капитал 1 млн ₽ (меняется), итоги хранятся с реплеем.
- ИИ-разбор: 70% — по календарному времени; «подтвердилась» — рост на скрытых 30% выше 95-го перцентиля 1 000
  случайных отказов и улучшение у ≥ 60% ликвидных бумаг.

**Зависит от:** G1, B3, B5, B8, D2, C3, модуль ИИ. **Влияет на:** C3 (учёт проб), работу со стратегиями.
