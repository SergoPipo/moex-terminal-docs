## Что сделать

1. **`scripts/staging.sh`** — тестовый стенд на копии рабочей БД, порты backend **8211**, frontend **5384**:
   - `reset <коммит | тег | ветка>` — только при остановленном стенде (иначе отказ). Worktree кандидата на этом коммите
     (detached), его зависимости, свежая копия рабочей БД, `alembic upgrade head`, подготовка копии (п. 2). В конце —
     коммит кандидата, голова alembic, какие сессии поставлены на паузу.
   - `up` — backend и frontend в фоне, отвязанно от сессии Claude и вкладки терминала; ждёт health и Vite; печатает
     `status`. Отказ, если нет копии БД или порты 8211/5384 заняты.
   - `down` — остановить оба процесса, убедиться, что оба порта свободны.
   - `status` — коммит кандидата, pid, health backend, ответ frontend, голова alembic копии.
2. **Подготовка копии** (Python-скрипт или модуль — на выбор сборки, с автотестами):
   - копия — только `sqlite3.Connection.backup` (gotcha-19), источник `file:/Users/sergopipo/MoexTerminal/data/terminal.db?mode=ro`
     (без `immutable`: рабочая БД под WAL), затем `pragma integrity_check`; отказ, если цель — рабочая БД или любой файл
     в `~/MoexTerminal/data`; старые `-wal`/`-shm` цели удаляются перед копией;
   - после миграций — сессии **sandbox и real** копии на паузу тем же механизмом, что и «Пауза» в интерфейсе (найти в
     коде; статусы — `trading/schemas.py`, `VALID_STATUSES`); paper-сессии не меняются; проверить, что
     `restore()` не поднимает приостановленные;
   - пользователю `sergopipo` в **копии** — тестовый пароль, как в образце `s8r-evidence/obs/prepare_obs_copy.py`
     (генерируется один раз, хранится в файле 0600 в каталоге данных стенда, не печатается; счётчики блокировки —
     сброс).
3. **Каталоги:**
   - код кандидата — worktree `Develop/.claude/worktrees/staging`;
   - данные стенда — `Develop/.claude/staging-data/` (копия БД, `backups/`, `logs/`, `tax_reports/`, pid-файлы, файл входа,
     признаки зависимостей); в worktree стенда `backend/data`, `backend/backups`, `backend/logs` — ссылки туда, как у
     `~/MoexTerminal/app` (код пишет `data/.last_shutdown_at` и `data/tax_reports` относительно `backend/`);
   - зависимости — свои у worktree стенда: `backend/.venv` (Python 3.11, по §7а
     `/Users/sergopipo/Documents/Claude_Code/Moex-Terminal/Документация по проекту/deployment_guide.md`) и
     `frontend/node_modules` (`pnpm install --frozen-lockfile`, Node 24); переустановка — только если изменились
     `backend/requirements.lock` или `frontend/pnpm-lock.yaml`. Venv `Develop/backend/.venv` (им пользуется стенд
     наблюдений) и зависимости `~/MoexTerminal/app` не трогать и не использовать.
4. **Окружение backend стенда:**
   - `.env` рабочего терминала — через `MOEX_ENV_FILE=/Users/sergopipo/MoexTerminal/app/.env` (файл читает только сам
     backend: ключ шифрования брокерских ключей копии нужен для графиков и сверки), как в образце

- Коммиты — только в ветке `feat/008-b0-release-contour` этого worktree. push, pull request, мерж в `develop`, теги и
  выкатка в рабочий терминал — только по моей команде.
- Правила проекта — `CLAUDE.md` этого репозитория (ветки, гейты, gotchas) и

- `.env`, токены, пароли, ключи — не читать, не печатать, не записывать.
- Рабочая БД `~/MoexTerminal/data/terminal.db` — только чтение через backup API (`mode=ro`). Файл
  `Develop/backend/data/terminal.db.moved-2026-10-23` — прежняя рабочая БД для отката, не трогать.
- Рабочий терминал (порты 8000/5173, каталог `~/MoexTerminal`) и стенд наблюдений (порты 8111/5284, worktree `s8r-obs`,
  `s8r-scen`, `s8r-evidence/obs`) — не останавливать, не перезапускать, их файлы не трогать. `scripts/start.sh` в
  `Develop/` не запускать: он займёт порты рабочего терминала. Свои временные процессы и файлы — убрать после себя;
  стенд после проверок оставить остановленным (`down`), каталог его данных — оставить.
- Порты проверять по одному на вызов `lsof`: с двумя `-i` он возвращает 1, если свободен хотя бы один порт
  (ошибка найдена 23.10 в `stand.sh`).
- Ордера — никогда на реальные счета; в этом блоке ордера не нужны вовсе, sandbox #3 тоже не трогать. Лимиты T-Invest
  общие на токен с рабочим терминалом — массовую загрузку истории на стенде не запускать.
- Новые зависимости Python и Node не добавлять; venv стенда ставится только из lock-файлов кандидата.
- Каждая команда `staging.sh` и каждая функция подготовки копии вызываются в рабочем пути (интеграционная проверка из
  `Спринты/prompt_template.md`): неподключённое — «⚠️ NOT CONNECTED», такая сборка не принимается.

## Приёмка блока

- Автотесты подготовки копии (pytest): отказ на рабочую БД и на файлы `~/MoexTerminal/data`; копия через backup API и
  `integrity_check`; пауза sandbox и real, paper без изменений; пароль меняется только в копии; повторный `reset`
  перезаписывает копию начисто.
- `bash -n` и `shellcheck` (если установлен) по `scripts/staging.sh`; гейты из `CLAUDE.md` этого репозитория для
  затронутого кода — зелёные и не ниже baseline.
- **Живой прогон** (обязателен, результат — в отчёте): `staging.sh reset v1.0.0` → `up` → health 200 на :8211,
  frontend 200 на :5384, в журнале стенда `session_runtime_restore_complete` и нет ошибок; список сессий копии и их
  статусы (sandbox и real — `paused`); Telegram и почта выключены (чем подтверждено); вход тестовым паролем через API;
  `status`; `down` → оба порта свободны; повторный `reset` поверх и снова `up`/`down`. Всё это время рабочий терминал —
  тот же pid в `~/MoexTerminal/data/stand.pid` и health 200 на :8000, стенд наблюдений — health 200 на :8111.
- В отчёте сборки — раздел «Для заказчика»: команды, пути, где файл входа, как подключить тестового бота, сколько
  длится `reset` с установкой зависимостей и без.

### §4. Тестовый стенд: проверка кандидата

1. `staging.sh reset <коммит>` — worktree на кандидате, свежая копия рабочей БД, миграции, пауза sandbox и real.
2. Гейты кандидата (если не прогнаны на том же коммите) и E2E затронутых сценариев.
3. Проверки блока из §5 и из раздела «Для тестового стенда» отчёта сборки Autopilot; результат — в отчёт блока
   (`s8r-evidence/008/<код>/`, не коммитится).
4. Живые проверки, которым нужно время (выходные, часы торгов, отсечки), — с датой, когда их можно сделать; блок
   принимается по ним или с явным решением заказчика «принять без».
5. Итог: «принят» → тег и выкатка; «не принят» → исправление в ветке блока и повтор с п. 1.

Telegram на стенде выключен: один бот не обслуживает два backend. Проверки Telegram (`/stopall`, повтор доставки,
сигналы) — отдельным тестовым ботом, токен которого заказчик сам вписывает в `.env` стенда, или после выкатки.
