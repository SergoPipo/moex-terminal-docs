## 1. Конвейер

```
 блок N    разработка ─► сдан ─► develop ─► тестовый стенд ─► принят ─► тег vX.Y.0 ─► рабочий терминал
           Autopilot     отчёт   PR, мерж    кандидат = коммит   проверки   по команде   выкатка по команде
           в worktree    сборки  по команде  мержа, копия БД     блока
 блок N+1               └─► разработка начинается, как только блок N сдан
```

1. **Один блок — один прогон Autopilot.** Сессия открывается **в папке worktree блока**
   (`Develop/.claude/worktrees/008-<код>`), а не в корне Moex-Terminal: Autopilot настраивает git-репозиторий рабочей
   папки сессии. Запуск — `/autopilot semi strict "<абсолютный путь к брифу блока>"`: `semi` — вопросы только на
   настоящих развилках, `strict` — ничего сверх плана 008.
2. **Коммиты Autopilot — в ветке блока** (`feat/008-<код>-<slug>`). push, pull request, мерж в `develop`, тег и выкатка —
   только по команде заказчика.
3. **В `develop` — один кандидат за раз.** Следующий блок мержится, когда предыдущий кандидат принят (тег) или
   отклонён. Разработка следующего блока при этом не ждёт: она идёт в своей ветке.
4. **Параллельно — не больше двух прогонов Autopilot**, каждый в своём worktree и своей сессии, с непересекающимися
   зонами файлов (обычно один блок A и один блок Б). При мерже второго — конфликт `.autopilot/PROGRESS.md` решается
   объединением обоих.
5. **После сдачи блока** та же сессия, уже без Autopilot, по команде заказчика: PR → мерж в `develop` → тестовый стенд
   (§4) → документация в репозитории docs (статус блока в §5, ФТ и ТЗ при изменении поведения — шапка версии и таблица
   истории, `ui_checklist_s8.md` в обеих копиях, `project_state.md`) → тег и выкатка (§3).
6. **Бриф следующего блока** готовит сессия, сдавшая предыдущий: файл `briefs/<код>_<slug>.md` по образцу
   [A-01](briefs/A-01_bar_storage.md) (шапка с целью, границами, правилами и приёмкой + дословные тексты пунктов 008),
   worktree и ветка от `develop`; заказчику — готовая строка `/autopilot …` и папка для новой сессии.
7. **Зависимости.** У рабочего терминала с 23.10 свой venv и `node_modules` (`~/MoexTerminal/app`). Venv
   `Develop/backend/.venv` до 10.12 использует стенд наблюдений (`obsstand.sh`) — новые пакеты туда не ставятся; блоку,
   который меняет зависимости, — свой venv в worktree.
8. **Правила проекта действуют полностью**: `CLAUDE.md` обоих репозиториев, решения заказчика, «.env не читать»,
   «рабочую БД не менять», sandbox #3 — по согласованным параметрам, реальные счета — только заказчик.

## 3. Выпуск и откат

**Нумерация:** `v1.0.0` — рабочий коммит на 2026-10-23 (`develop` `76480cc`); каждый принятый блок — следующий минорный
выпуск (`v1.1.0`, `v1.2.0`, …); исправление после выкатки — третья цифра. Тег ставится на проверенный коммит-кандидат.

**Выкатка** (по команде, окно не нужно, пока нет real-сессий):
1. Остановка рабочего терминала по pid-файлу.
2. Снимок рабочей БД через `sqlite3.Connection.backup` → `terminal.db.bak-<дата>-pre-<тег>`.
3. `git checkout <тег>` в `~/MoexTerminal/app`; зависимости — если менялись lock-файлы (`deployment_guide.md`, §7а).
4. Запуск; проверка: health, `session_runtime_restore_complete`, журнал без ошибок, короткий осмотр по списку блока.

**Откат:** остановка → `git checkout <прошлый тег>` → восстановление снимка БД (если миграции выпуска уже применились) →
запуск. Данные, записанные после снимка, при восстановлении теряются — это записывается в отчёт выкатки.

## 4. Тестовый стенд: проверка кандидата

1. `staging.sh reset <коммит>` — worktree на кандидате, свежая копия рабочей БД, миграции, пауза sandbox и real.
2. Гейты кандидата (если не прогнаны на том же коммите) и E2E затронутых сценариев.
3. Проверки блока из §5 и из раздела «Для тестового стенда» отчёта сборки Autopilot; результат — в отчёт блока
   (`s8r-evidence/008/<код>/`, не коммитится).
4. Живые проверки, которым нужно время (выходные, часы торгов, отсечки), — с датой, когда их можно сделать; блок
   принимается по ним или с явным решением заказчика «принять без».
5. Итог: «принят» → тег и выкатка; «не принят» → исправление в ветке блока и повтор с п. 1.

Telegram на стенде выключен: один бот не обслуживает два backend. Проверки Telegram (`/stopall`, повтор доставки,
сигналы) — отдельным тестовым ботом, токен которого заказчик сам вписывает в `.env` стенда, или после выкатки.
