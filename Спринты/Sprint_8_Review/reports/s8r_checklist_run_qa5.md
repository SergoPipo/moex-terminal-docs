## Дефекты

**Д-1 (S8.50 п.5, ❌; severity medium; глобально для всех экранов < 768 px).** На телефоне навигация закрывает всё содержимое страницы.
Шаги: окно 320×640 → `/settings?tab=risk` (и любой другой экран). Ожидалось: форма видна, меню скрыто/открывается бургером. Получено: `AppShell.Navbar` шириной 320 px поверх `main`; бургер переключает 240↔60 px, что ниже брейкпоинта не действует; `elementFromPoint` центра «Сохранить» = `NAV`.
Диагноз: `frontend/src/components/layout/AppShell.tsx:15-18` — `navbar={{ width: collapsed ? 60 : 240, breakpoint: 'sm' }}` без `collapsed: { mobile: … }`; ниже `sm` Mantine делает навбар на 100 % ширины и прячет его только при `collapsed.mobile`. `Header.tsx:114` — бургер вызывает `toggleSidebar` (ширина), а не мобильное открытие/закрытие. Существующий e2e `e2e/s5-circuit-breaker.spec.ts:104` меряет только ширину панели и этого не видит.

**Д-2 (попутно к S8.58 п.7; severity medium).** Детект дивидендов молча ничего не находит.
`GET https://iss.moex.com/iss/securities/{LKOH,SBER}/dividends.json` сейчас отдаёт блоки `description` и `boards`, блока `dividends` нет. Продуктовый `_fetch_iss` на копии (`iss_div.py`): `{"LKOH": 0, "SBER": 0, "GAZP": 0, "MTSS": 0}` строк дивидендов, при этом сплиты приходят (57 строк). В копии последние дивиденды заведены 2026-04-22 — тогда источник работал.
Диагноз: `backend/app/corporate_actions/service.py:966` — `raw.get("dividends", {})` превращает отсутствие блока в пустой список без единого warning'а. Нужны предупреждение об отсутствии блока и решение по источнику (например, T-Invest `GetDividends`). Риск рядом: `_store_dividends` (`:1060-1086`) не фильтрует по дате — в апреле одним проходом заведена вся история LKOH с 2013 года. Если уведомления будут слаться по каждой новой строке, при первом детекте нового тикера пользователь получит десятки уведомлений о давно прошедших дивидендах.

**Д-3 (попутно к S8.54 п.4 и S8.49 п.2; severity low).** Нечитаемый ключ брокера (порча шифртекста, ротация `ENCRYPTION_KEY`) даёт пустые или вводящие в заблуждение тексты.
(а) Telegram `/balance`: блок счёта «❌ » без текста — `notification/telegram_webhook.py:738` `str(account_error)` пуст для `cryptography.exceptions.InvalidTag`. (в) Причина в close-all «…, **брокер** не вернул текст» (`trading/engine.py:1194`), хотя до брокера дело не дошло — сбой расшифровки ключа. (г) Лог `close_all_positions_close_failed reason=` по-прежнему пуст (`engine.py:8038` пишет `str(close_exc)`, а не `close_failure_reason`). Остаток фронта: `PauseConfirmModal.tsx:60` всё ещё `r.reason ?? …` (пустую строку не ловит). Сейчас это безопасно — backend гарантирует непустую причину.

**Д-4 (попутно; severity medium, данные).** Восстановление sandbox-счёта привязывает запись одного пользователя к счёту, уже закреплённому за записью ДРУГОГО пользователя.
В копии на `GET /broker-accounts/4/sandbox-balance` (дашборд testuser1, 17:37:57) лог `sandbox_account_reopened broker_account_id=4 stale=8de9093c… new=f925da17…`. Теперь записи #3 (sergopipo) и #4 (testuser1) указывают на один живой sandbox-счёт `f925da17`. Ордеров не было.
Диагноз: `broker/sandbox_recovery.py:356-381` `_account_ids_taken_by_siblings` отбирает занятые счета только по `user_id` записи. Комментарий там же описывает последствия: двойной баланс и позиции, закрытие одной записи «съест» позицию другой. На рабочем стенде запись #4 в бэкапе со stale `8de9093c`, то есть первый же заход testuser1 сделает то же самое. Затронуты сессии #4/#6 testuser1 (остановлены).

## Как обеспечена безопасность и что изменено в копии

- Ордера: ни одного. Единственное брокерское действие в сценарии закрытия (S8.54 п.4) шло при испорченном ключе #3, и backend перезапускался после порчи, чтобы в памяти не осталось расшифрованного клиента. Перед кликом спека проверяла, что ключ не читается (`sandbox-balance` 500), иначе останавливалась. Pending-сделка (S8.58 п.5) создавалась при том же испорченном ключе.
